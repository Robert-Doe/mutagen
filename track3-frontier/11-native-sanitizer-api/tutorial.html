The Native Sanitizer APIdoes the platform fix hold?

Element.setHTML() ships in Chrome 148. It is mutation-safe by construction: one parse, filter the tree, insert. No serialize step means no second parse for a sink-differential to exploit. Every course vector, run through the real API — nothing fires.

What this module proves

The entire mutation-XSS class comes from parse → serialize → parse. Remove the middle step — hand the caller a tree, never a string — and the class has nowhere to live. setHTML() does exactly that.

01

The Big Analogy

For years, Kofi's process was: open the crate, check it, nail it shut again, and send the sealed crate on. Every problem in this course came from that last step — the crate being re-opened downstream by someone with a different rulebook.

The new process: Kofi opens the crate, checks it, and wheels the contents straight onto the shop floor himself, on an open pallet. There is no crate to re-open, no manifest to re-read, no downstream officer with a different rulebook. What he checked is what goes on the shelf, exactly. The failure mode is gone because the step that caused it is gone.

02

What Happens, Step by Step

element.setHTML(str, { sanitizer }):

  1. Parse str as a fragment, context = element, scripting disabled during the parse (so <script> never runs, even transiently) — but the <noscript> content model matches the live document, closing Module 4.
  2. Walk the resulting tree against the sanitizer config (an allow/block list of elements and attributes; a built-in default that drops all script-capable surface).
  3. Insert the filtered nodes into element. No serialization. The tree that was filtered is the tree that is now live.

Compare Track 2: parse → filter → serialize to a string → the app assigns that string to innerHTML → the browser parses it again. Steps 3–5 are where every mutation in this course happens. setHTML has no steps 3–5.

04

The Code, Explained

// the shape, modelled — src/native.mjs
export function setHTMLModel(html, safe) {
  const tree = parseFragment(html, 'div', { scripting: true });   // ONE parse
  filterInPlace(tree, safe);                                       // filter the TREE
  return tree;                                                     // insert as-is — NO serialize
}

The two escape hatches, and their real risk:

element.setHTMLUnsafe(str)      // parses (no script exec), does NOT filter
Document.parseHTMLUnsafe(str)   // same, at document level
// still single-parse → still mXSS-immune. residual risk is a plain
// <img onerror> the caller forgot to handle — an ordinary DOM-XSS, not a mutation.

05

Limits / What You Cannot Do Yet

Can't do yet (or ever, with setHTML)

  • Mount a mutation-XSS attack — there is no round trip
  • Rely on it in every browser today — Safari support lags; ship a polyfill/DOMPurify fallback
  • Use setHTMLUnsafe and skip thinking — it doesn't sanitize

Can do

  • Verify all 12 course vectors are inert through the real API
  • Explain why it's immune, not just that it is: no serialize step
  • Locate sanitisation correctly — it's one layer; CSP + Trusted Types are the others

07

Brain Exercise

If setHTML() ends the mutation-XSS class, is the rest of this course now obsolete?

No — for three reasons. (1) Deployment reality: billions of lines of existing code use innerHTML + DOMPurify and will for a decade; understanding their failure mode is the job. (2) The API has a config surface: setHTML({ sanitizer: { elements: [...] } }) — allow-list <style> or <svg> and you've re-opened Modules 3 and 5 inside the safe API, because now its filtered tree contains a mutating element that a later .innerHTML read of that subtree would serialize. (3) It's one layer: a bug in the sanitizer config, a setHTMLUnsafe call, a non-setHTML sink somewhere in a dependency — and you're relying on Trusted Types and CSP to catch it. Sanitising is the last line, never the only one. That hand-off is where this course ends and bob_CSP_trusted_types begins.

08

There Are No Dumb Questions

Q: Does DOMPurify become pointless?
A: It gains a native fast path and stays as the cross-browser fallback and the richer-config option. cure53 has said as much. For new code targeting modern browsers, setHTML() first, DOMPurify fallback.
Q: Why does the default setHTML() keep <title> but empty its content?
A: The default allow-list includes <title> as a structural element but drops disallowed children; and since its content model is RCDATA, what remains serialises escaped. Net effect: inert. You saw it in the state map.
Q: Is Sanitizer (the object) the same as setHTML?
A: Sanitizer is the reusable config object you can pass to setHTML (and parseHTML). setHTML is the sink that applies it. The config is where you can help or hurt yourself — see the brain exercise.
