Reading Disclosuresa repeatable dissection

Given a new mutation-XSS write-up, four questions get you from "scary payload" to "here is the one step that, if changed, closes it" — and then to which historical patch changed exactly that step.

The four questions

Q1 what does the sanitizer's parse produce?   Q2 what does the serializer emit?   Q3 what does the browser's re-parse produce?   Q4 which single step is the hinge?

The Big Analogy

An inspector at another port files a report: "crate #4471 got through — contained a rifle." Panic, or method? Method: pull the four records. The arrival manifest (Q1: what the first officer logged). The transfer manifest (Q2: what got written when it was moved). The delivery manifest (Q3: what the final officer read). Lay them side by side and one line will have changed between two of them — that line is the hinge (Q4). Then check the rulebook: which amendment governs that line, and was it in force at this port?

02

The method, worked on the <noscript> disclosure

Payload: <noscript><p title="</noscript><img src=x onerror=alert(1)>">

  1. Q1 — sanitizer parse (scripting off): noscript > p[title="</noscript><img…>"]. A <p> with a title. Safe.
  2. Q2 — serialize: 2019: title="</noscript><img…>" (raw). 2026: title="&lt;/noscript&gt;&lt;img…&gt;".
  3. Q3 — browser re-parse (scripting on): 2019: RAWTEXT sees literal </noscript> → breaks out → live <img>. 2026: RAWTEXT never decodes &lt; → inert.
  4. Q4 — hinge: Q2. The serializer's attribute escaping. Patch: Chrome/Firefox escape </> in attribute values (~2020); DOMPurify added a dedicated <noscript> check.

Our engine's dissect() runs Q1–Q4 and, for this payload, reports mutates: false — because it models the 2026 serializer. That's the honest answer: on a current browser this exact payload is patched. The method is what transfers.

The Code, Explained

export function dissect(payload, {sanitizerContext='template', sinkContext='div'}) {
  const q1 = parseFragment(payload, sanitizerContext, {scripting:false});   // Q1
  const serialized = serialize(q1);                                          // Q2
  const q3 = parseFragment(serialized, sinkContext, {scripting:true});       // Q3
  const mutates = !hasLiveHandler(q1) && hasLiveHandler(q3);                  // safe→dangerous?
  return { ..., q4_hinge: mutates ? classifyHinge(payload, serialized) : 'does not mutate' };
}

classifyHinge pattern-matches the payload + serialized string against the five mechanism families (raw-text, namespace, scripting flag, attribute, template). Rationale: DECISIONS.md.

Limits / What You Cannot Do Yet

Can't do yet

  • Auto-dissect a payload whose mechanism our engine doesn't model (e.g. a brand-new insertion-mode bug)
  • Reproduce a bypass against the exact vulnerable library version — you'd npm i dompurify@2.0.16 for that

Can do

  • Run Q1–Q4 on any payload and get a named hinge
  • Tell "mutates" from "plain DOM XSS" from "benign"
  • Honestly report which historical bypasses are patched vs. still-live-against-naive-code in 2026

07

Brain Exercise

Our dissect() reports the <noscript> and CVE-2020-26870 payloads as mutates: false — because it models the 2026 serializer. A researcher reads a 2019 write-up that says these do fire. Who's right?

Both, in their own time frame. This is the single most important habit in reading mXSS disclosures: always pin the browser version and the library version. A payload is not "an mXSS" in the abstract — it's an mXSS against a specific (browser serializer, sanitizer) pair. The 2019 write-up is correct for Chrome-2019 + DOMPurify-2.0.16. Our engine is correct for Chrome-148 + a correct sanitizer. The mechanism (Q4 hinge) is the durable knowledge; the fires / doesn't fire verdict has a date on it. When you reproduce a disclosure, reproduce the environment too, or your "it's patched!" is as unreliable as their "it fires!" would be today.

08

There Are No Dumb Questions

Q: Where do I find the patch commit for a disclosure?
A: DOMPurify's CHANGELOG.md tags security releases; each links the GitHub issue, which links the fix PR. For browser-side patches, the payload usually stopped working in a specific Chromium/Gecko version — bisect chromium-dash or check the linked crbug.
Q: Is classifyHinge just a lookup table?
A: Yes — five regexes over the payload and the serialized string, one per mechanism family. That's the point: after Modules 3–7 there are only five families, and a new disclosure is almost always a new instance of one, not a new family.
Q: What if a disclosure is a genuinely new family?
A: Then it's a paper, not a blog post. Heiderich 2013 named the field; the Sanitizer API is arguably the last structural change. New families are rare; when one appears, it usually traces to a new browser parser feature (declarative shadow DOM was the most recent candidate).
