The second prerequisite the sibling courses never needed. Module 4 — the Google Search 2019 bug — is entirely this one idea.

☞

Sekondi

The customs rulebook at Sekondi has a clause that reads differently depending on whether the harbour generator is running. Power on: a drum marked "backup fuel — ignore unless power fails" is sealed and set aside unopened; the whole label and contents are one inert lump. Power off: that same drum is opened and its contents sorted item by item.

Kofi checks crates at the shed, where the generator is usually off, so he opens the drum. The ship's inspector checked the same crate at sea with the power on, so she left it sealed. Two competent inspectors, one rulebook, one crate — and a completely different decision about what is inside it. The element that behaves this way is <noscript>.

01

What the flag is

The HTML parsing algorithm takes an input the standard calls the scripting flag. It is enabled or disabled, fixed for the whole parse. It affects the tree in exactly one place: the content model of <noscript>.

Scripting flagHow <noscript> content is parsed
enabledRAWTEXT — everything up to </noscript> is one text node. No tags, no entities.
disabledNormal — the content is parsed as ordinary markup, elements and all.

The logic is reasonable in isolation. <noscript> holds fallback content shown only when scripting is off. If scripting is on the browser will never render it — so don't build a DOM for it, treat it as text. If scripting is off, it's about to be shown, so build the real DOM.

02

Who sets it to what

EnvironmentFlagWhy
A real browser rendering a pageenabledJavaScript runs there.
element.innerHTML = … in a live pageenabledSame document, scripting on.
new DOMParser().parseFromString(…, 'text/html')disabledThe result is inert — scripts never run in it.
<template> contentdisabledTemplate content is inert by design.
jsdom / a server-side DOM in Nodedisabled (default)No scripting environment unless you opt in.
DOMPurify running server-side on jsdomdisabledInherits jsdom's default.
There is the whole bug

A sanitizer very often runs with the scripting flag disabled — server-side on jsdom, or client-side via DOMParser / <template>. The browser that finally renders the sanitized output has it enabled. Feed <noscript> content that is inert markup under one flag and live markup under the other, and the sanitizer inspects a different tree from the one that runs.

03

Seeing it happen

input  =  <noscript><img src=x onerror=alert(1)></noscript>

scripting DISABLED   (new DOMParser().parseFromString(..., 'text/html'))
  noscript.childNodes   ->  [ <IMG> ]              a real element
  noscript.innerHTML    ->  '<img src="x" onerror="alert(1)">'

scripting ENABLED    (div.innerHTML = input, in a live document)
  noscript.childNodes   ->  [ #text ]               just text
  noscript.firstChild.nodeValue  ->  '<img src=x onerror=alert(1)>'

Same seven-word string. One parse contains an image element with an event handler; the other contains the characters of that string and nothing else. Our engine's parseFragment(html, 'body', {scripting}) reproduces both.

04

Why the minimal case above is not yet the exploit

In that exact example a competent sanitizer running with scripting disabled sees the <img onerror> and strips the handler — so its output is safe. The real <noscript> attacks smuggle the payload somewhere the disabled-flag parser reads as an inert attribute value (so the sanitizer waves it through) while the enabled-flag parser, treating the whole block as RAWTEXT, sees a </noscript> that ends the text early and live tags after it. That is Module 4 — tested against the browser you actually have, because browsers have patched specific vectors over the years.
