The Serializerand why it won't round-trip

A sanitizer never hands the browser a tree. It hands it a string, produced by the innerHTML getter. This module builds that algorithm and shows the first case where parse(serialize(parse(x))) comes back as something parse(x) never was.

What this module proves

Serialization is not the inverse of parsing. It normalises some things, escapes others, and — for <style>, <script>, <xmp>, <noscript> — escapes nothing. So the string you check is not always the string the browser parses.

01

The Big Analogy

Kofi opens a crate, checks everything, and writes a fresh manifest before nailing it shut for the next leg. The rules for writing a manifest are not the same as the rules for reading one. When he reads, a comma in a product name is just a comma. When he writes, he is told to put quotes around any field with a comma in it — so the field knives, 6 inch gets written as "knives, 6 inch". Read that back and you get the same thing. Fine.

But there is a shortcut clause. For bulk cargo — sand, gravel, scrap — Kofi is told not to bother quoting anything, just copy the weight ticket through verbatim. Now suppose someone slips a weight ticket that reads gravel 40kg” contraband 5kg “. Kofi copies it through unquoted, because that's the rule for gravel. The next officer reads it and sees two line items. The manifest changed meaning between writing and reading — not because anyone lied, but because the write rule and the read rule don't line up for bulk cargo. <style> and <xmp> are the bulk cargo.

02

What Happens, Step by Step

The innerHTML getter (WHATWG §13.3, "serialising HTML fragments") walks the node's children in order:

  1. Text node → if the parent is <style>, <script>, <xmp>, <iframe>, <noembed>, <noframes>, <noscript>, <plaintext>: emit the data verbatim. Otherwise: replace &→&amp;, U+00A0→&nbsp;, <→&lt;, >→&gt;.
  2. Element → <name, then each attribute as  name="value" where the value has &, U+00A0, " escaped — and, in browsers since ~2020, < and > too. Then >. Then serialise the children. Then </name> — unless the element is void (<img> <br> <input>…), which gets no close tag and no children.
  3. Comment → <!--data-->. (The data is not escaped — another place things can go wrong.)

The spec's own note on this section: the output "might not round-trip" — parsing it can yield a different tree. It says so in plain text. [R3]

04

The Code, Explained

engine/mxss-lab/lab.mjs, the whole serializer that matters:

const NO_ESCAPE_TEXT = new Set(['style','script','xmp','iframe',
  'noembed','noframes','noscript','plaintext']);

function serialize(node) {
  let out = '';
  for (const child of kidsArray(node)) {
    if (child.type === 'text') {
      const parent = node.name?.toLowerCase();
      out += NO_ESCAPE_TEXT.has(parent) ? child.data : escapeText(child.data);
    } else if (child.type === 'comment') {
      out += `<!--${child.data}-->`;
    } else {
      out += serializeElement(child);   // <name attr="..."> children </name>
    }
  }
  return out;
}

And the round-trip harness — the tool of this course:

function roundTrip(html, {contextTag='body', scripting=false, max=5}) {
  let cur = html; const steps = [html];
  for (let k = 0; k < max; k++) {
    const next = serialize(parseFragment(cur, contextTag, {scripting}));
    steps.push(next);
    if (next === cur) return {steps, stable:true, iterations:k+1};
    cur = next;
  }
  return {steps, stable:false, iterations:max};   // never settled — a red flag
}

07

Brain Exercise

The round-trip harness returns stable: false for some input — it re-serialised 5 times and never got the same string twice. Is that possible, and what would it mean for a sanitizer?

It is possible in principle (two shapes that each serialise into the other), and it is a catastrophic signal for a sanitizer. A sanitizer that runs "sanitise → serialise → re-parse → sanitise again, until stable" (Module 8, and DOMPurify's real strategy) relies on a fixed point existing. If none exists, the loop either runs forever or bails after N tries and ships a string it never fully checked. In practice browsers have removed the constructs that caused true non-termination (the 2024 <select> parsing change, covered in the Foster Parenting course, was partly for this). But "always cap the loop and treat a non-fixed-point as a hard reject" is exactly why Module 8's sanitiser has a max and throws.

08

There Are No Dumb Questions

Q: If the spec knows serialization doesn't round-trip, why not fix it?
A: A truly round-trip-safe serializer would have to escape inside <style>/<script> — but then the CSS/JS it contains would be corrupted (a > b selectors, x < y comparisons). Raw emission is the only thing that keeps those elements usable. The gap is load-bearing, not a bug.
Q: Is outerHTML the same algorithm?
A: Almost — outerHTML serialises the element itself plus its children; innerHTML only the children. XMLSerializer is a different algorithm again (XML rules: always self-close, namespaces explicit). Module 9 lines all seven up.
Q: Why does a<b>c come back as a<b>c</b> — nothing dangerous happened?
A: Nothing dangerous there. It is the smallest proof that serialize(parse(x)) ≠ x even for boring input, which is the premise every later module builds on. If the identity held, mutation XSS could not exist.
Q: Does the round-trip loop always terminate?
A: For the constructs this course covers, in current browsers, yes — usually in 1–2 rounds. The harness still caps at max and reports stable: false rather than looping, because "assume it terminates" is not a property you want a security control to depend on.
