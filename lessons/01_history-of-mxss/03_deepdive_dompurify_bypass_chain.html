The DOMPurify Bypass Chaingeneration by generation

DOMPurify did everything right — parse-based, allow-list, actively maintained — and still absorbed a decade of bypasses. Each one forced a specific, small, permanent change. This is that list.

02

The pattern in the fixes

Every DOMPurify security fix is one of exactly four moves — the same four Module 8 builds:

  1. Add to the forbidden list (an element or attribute whose contents or effect can't be safely serialized): <mglyph>, <template> by default, shadowrootmode.
  2. Tighten the namespace check: which element is valid in which namespace, and reject the rest.
  3. Fix the walk: static node list; re-check nodes that were mutated or clobbered during the pass; enter special sub-trees.
  4. Stabilize the output: the round-trip loop (later: rebuild from a stable serialization and diff).

New disclosure → identify which of the four it defeats → that's the fix. This is why Module 10's classifyHinge has five families and Module 8's sanitizer has four ideas: after a decade, the space is closed and small.

Finding the primary sources

  • DOMPurify CHANGELOG.md — security releases are tagged; each links a GitHub issue → fix PR → the exact diff.
  • research.securitum.com — Bentkowski's write-ups, with reproduction steps and the version they worked against.
  • cure53.de/pentest-report_dompurify.pdf and the DOMPurify wiki — design rationale for the four moves above.
  • Chromium/Gecko bug trackers — for the ~2020 attribute serialization change, search crbug / bugzilla for "serialize attribute value" + "<" ; the payload simply stopped working in a specific milestone.
