The Scripting Flagone boolean, two trees

A server-side sanitizer parses with scripting off. The browser parses with scripting on. For <noscript>, those are different trees — the Google Search 2019 bug. This module reproduces the mechanism and reports, honestly, which vectors survive in Chrome 148.

What this module proves

<noscript><img src=x onerror=alert(1)></noscript> parses to an element tree with scripting off and a text node with scripting on. A sanitizer inspects the first; the browser runs the second.

The Big Analogy

The Sekondi rulebook has a clause that reads differently depending on whether the harbour generator is running. Power on: the drum marked "backup fuel — ignore unless power fails" is sealed and set aside, whole. Power off: it's opened and every item sorted.

Kofi checks crates at the shed with the generator usually off, so he opens the drum, sees a box of knives, confiscates it, reseals. The ship's inspector checked the same crate at sea with the power on, so she left the drum sealed — and wrote on her manifest "one sealed fuel drum, contents not inspected". Now the drum reaches a port where the power is on. They read the ship's manifest, see "sealed, not inspected", and wave it through — knives and all. Two competent inspectors. The one who could see the knives wasn't the one whose paperwork counted.

02

What Happens, Step by Step

  1. Attacker submits <noscript><p title="</noscript><img src=x onerror=alert(1)>">.
  2. Server sanitizer parses, scripting off. <noscript> content is normal markup: a <p> whose title attribute is the string </noscript><img src=x onerror=alert(1)>. A <p> with a title. Utterly benign. Approved.
  3. Sanitizer serializes. In 2019, some serializers left the </> in that attribute alone. The browser (scripting on) re-parses: <noscript> content is RAWTEXT, the literal </noscript> ends it early, and <img src=x onerror=alert(1)> after it is a live element. XSS
  4. 2026: the modern serializer escapes that attribute to title="&lt;/noscript&gt;&lt;img…&gt;". RAWTEXT does not decode entities, so there is no literal </noscript> to break out on. This exact vector is dead.
Honest status, Chrome 148

Every <noscript> payload this module tries is blocked — by attribute escaping, or because the scripting-off sanitizer sees the <img onerror> as a real element and strips it. The mechanism is intact and still bites (a) string sanitizers, (b) sanitizers that allow <noscript>, (c) non-browser re-parsers (email, PDF). The proof page runs all of them.

07

Brain Exercise

DOMPurify runs in the browser (scripting on), not on a server. So the scripting-flag mismatch can't apply to it… right?

Wrong — and this is exactly how the Google 2019 bug worked. DOMPurify parses its input by assigning it to a detached element or a <template> / DOMParser document — and <template> content and DOMParser documents have the scripting flag disabled, even inside a live page. So DOMPurify inspects the flag-off tree, and the app's el.innerHTML = clean builds the flag-on tree. The mismatch is inside one browser tab. DOMPurify's fix (FORCE_BODY handling and later a dedicated <noscript> check) plus the browser serializer change closed it.

08

There Are No Dumb Questions

Q: Which other elements does the scripting flag affect?
A: Only <noscript>. That's the entire blast radius of the flag in the tree-construction algorithm. (It also gates whether <script> executes, but not how it parses.)
Q: If I set scripting: true in my server-side jsdom, does that fix it?
A: It makes your sanitizer's parse match the browser's for <noscript> — which is genuinely good and DOMPurify-on-jsdom docs recommend matching the deployment. But it's a config you have to get right; the robust answer is to forbid <noscript> outright (Module 8) or use the native Sanitizer API (Module 11), which has no separate parse step to mismatch.
Q: Is this the same as the <template> issue in Module 7?
A: Related — both are "the sanitizer's parsing context differs from the sink's". Module 7 is about content moving across the template boundary; this one is about a single flag flipping one element's content model. Different lever, same family.
