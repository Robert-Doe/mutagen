Namespace Confusionthe DOMPurify bypass family

The most famous mXSS class, and the one with live 2026 bypasses. Markup that is inert inside SVG or MathML becomes a live HTML handler once the foreign wrapper is stripped or the namespace boundary is miscomputed. Four vectors, each verified firing in Chrome 148.

What this module proves

A sanitizer that walks a live child list, or judges an element by tag name without its namespace, or forgets <image> ≡ <img>, ships a tree the browser turns into script. Snapshot + namespace enforcement + alias normalisation closes all four.

01

The Big Analogy

The fishing co-op's hall at Sekondi checks a crate and finds a drum of net-preservative — legal there. It stamps the crate and sends it on. Down the dock, a re-sort moves that crate into the General Goods stream. The General Goods officer never re-checks it — the co-op's stamp is right there. But net-preservative is a banned solvent in General Goods. It's through.

Four ways the re-sort happens. The clerk who counts by looking at the top label and moving on — if you slip a crate onto the pile while their finger is already past that spot, they never count it (the live-list bug). Judging by the product name and not the hall it came from — "drum of solvent" sounds fine if you don't ask which rulebook applied (no namespace check). Two names for one thing — the form says "IMG" is banned, but the crate is labelled "IMAGE" (the alias). And the crate that ejects itself — put a pallet of General Goods (<p>) in the co-op hall and security walks the whole lot out, solvent included, into General Goods (the breakout).

02

What Happens, Step by Step

Take the MathML vector <math><mtext><mglyph><style><img src=x onerror=alert(1)></style></mglyph></mtext></math>:

  1. <math> → MathML namespace.
  2. <mtext> → a text integration point — content would parse as HTML…
  3. …except <mglyph>, which is the exception: it stays MathML.
  4. So <style> is a MathML element — not rawtext — and <img src=x onerror=alert(1)> is a real child element of it (then <img>, a breakout tag, ejects to sit beside the style).
  5. A naive sanitizer unwraps <math><mtext><mglyph> (not on its list) while iterating a live list, and the promoted <img> is skipped by the iterator — its onerror never gets stripped.
  6. Serialize, re-parse at innerHTML: a live <img onerror>. XSS

The Code, Explained

The one bug that opens the door, in naiveSanitize:

for (const child of node.children) {        // iterating the array we splice below
  if (!allow.has(child.name)) {              // name only — no child.ns check
    kids.splice(i, 1, ...grandchildren);     // the promoted nodes are SKIPPED by for…of
  }
}

The three lines that close it, in correctSanitize:

const snapshot = [...node.children];              // 1. snapshot before mutating
if (child.ns !== HTML || !allow.has(name)) …      // 2. an element must be HTML-namespaced
if (name === 'image') { child.name = 'img'; … }   // 3. normalise the alias, then re-check

These three are exactly what DOMPurify does: _forceRemove on a snapshot, the _checkValidNamespace gate (added after CVE-2020-26870-era bypasses), and a fixed list of "tags that browsers rename". DECISIONS.md maps them line by line; Module 8 builds the full hardened sanitizer.

07

Brain Exercise

The "correct" sanitizer enforces child.namespaceURI === HTML_NS. An attacker submits <svg><foreignObject><img src=x onerror=alert(1)></foreignObject></svg>. The <img> inside <foreignObject> is in the HTML namespace (integration point). Does it get through?

The <img> passes the namespace check — but the <svg> and <foreignObject> above it do not. They're SVG-namespaced, so the sanitizer unwraps them, promoting the (HTML) <img> to the fragment root — where it is now an ordinary allowed <img> and its onerror gets stripped by the attribute filter. So: blocked, but by the attribute scrub, not the namespace check. The lesson: namespace enforcement alone isn't enough — you still need the per-element attribute allow-list to run on every surviving node, including ones promoted out of removed parents. Module 8's loop is what guarantees that.

08

There Are No Dumb Questions

Q: These fire against a "naive" sanitizer I wrote for the demo. Did real DOMPurify ever fall for them?
A: Yes — earlier versions. CVE-2020-26870 (the <svg></p><style> shape) worked on DOMPurify < 2.0.17. The <form> and <mglyph> shapes trace to Bentkowski's 2019 write-ups. Each was patched with exactly the defensive line this module shows. Module 10 reproduces the disclosures with their patch commits.
Q: Why is <image> even a thing?
A: A very old HTML quirk — <image> was an early synonym for <img> that some 1990s browsers supported, and the parser still maps it for compatibility. It's a permanent gotcha for any allow-list that stores tag names as strings.
Q: If I just forbid <svg> and <math> entirely, am I safe from this module?
A: From these four, largely yes — and that's a legitimate hardening (Module 8 does it). But you lose inline SVG, which many apps want. The namespace check lets you keep SVG shapes while dropping SVG scripting surface. It's the more surgical fix.
