The Big Analogy

Kofi's supervisor rewrites the whole procedure after a bad year. One: after you seal a crate, unseal it and re-check it — and repeat until a re-check finds nothing new. If it never stabilises, refuse the crate entirely. Two: every item is checked against the General Goods rulebook, no matter which hall it arrived in — a co-op stamp buys you nothing. Three: certain container types — sealed drums, sample crates, diplomatic pouches — are just not accepted; tip the contents out and check those, or turn the lot away. Four: the item checklist runs on every item that ends up on the table, including ones that fell out of a container you removed.

02

What Happens, Step by Step

  1. Pass: parse (scripting off) → walk a snapshot of every child list → for each element:
    • on the forbidden list (style script xmp noscript noembed noframes iframe title textarea template mglyph malignmark annotation-xml) → drop it and its subtree;
    • not in the HTML namespace → drop it, keep cleaned children;
    • not on the allow-list → unwrap (keep cleaned children);
    • allowed → keep, but filter attributes: no on*, no style=, allow-list only, no javascript:/data: URLs.
    → serialize.
  2. Loop: feed that string back through the pass. If it equals the previous output — a fixed point — ship it. If not, go again.
  3. After max passes with no fixed point: throw. A string that won't stabilise is a string you cannot vouch for.

The Code, Explained

The loop, in engine/mxss-lab/sanitizers.mjs:

export function hardenedSanitizer(html, opts) {
  let cur = String(html);
  for (let i = 0; i < (opts.max ?? 6); i++) {
    const next = onePass(cur, opts);
    if (next === cur) return next;          // fixed point — safe to ship
    cur = next;
  }
  throw new Error('no fixed point after ' + max + ' passes — rejecting input');
}

One pass, the load-bearing checks:

if (FORBIDDEN.has(name)) continue;                 // drop subtree
if (child.ns !== HTML) continue;                   // namespace gate
if (!allow.elements.has(name)) { hoistCleanChildren(); continue; }   // unwrap
child.attrs = child.attrs.filter(scrub);           // per-node attribute allow-list

Limits — What You Cannot Do Yet

Can't do yet

  • Guarantee safety against a future browser parser change — a new mutation could need a new forbidden entry
  • Stop the payload if a bypass does land — sanitising is the last line, not the only one (Module 11, then CSP)

Can do

  • Close all 12 course vectors, verified, while preserving benign HTML
  • Reject (not silently ship) any input that won't reach a fixed point

Getting a blank or broken result?

"no fixed point after 6 passes — rejecting input" on a payload you expected to clean — that's the loop working. Either the input genuinely doesn't stabilise (reject it) or raise max if you have a legitimate reason to expect >6 rounds (you almost never do).

07

Brain Exercise

The hardened sanitizer forbids <style> outright. But lots of apps — email clients, CMS — legitimately need scoped <style>. How would you allow it without re-opening Modules 3 and 5?

Keep the element but treat its text content as a separate sanitisation problem with its own rules: parse the CSS, drop @import, expression(), url(javascript:…), -moz-binding, and — the mXSS-specific part — verify the serialised CSS contains no </style substring (case-insensitively, entity-normalised) that could close the element early on reparse. If it does, re-encode or reject. This is exactly what DOMPurify's SAFE_FOR_XML and its dedicated _isValidAttribute-for-style path do, and why enabling <style> in DOMPurify pulls in a CSS parser. The general principle: if you must allow a mutating element, you take on the job of proving its serialisation round-trips, per element, forever.

08

There Are No Dumb Questions

Q: Does real DOMPurify actually run a loop?
A: Early versions had an explicit do { ... } while (dirty). Current versions removed it because they rebuild the DOM from a stable serialisation and re-check for nodes mutated/clobbered during the walk — which gives the same fixed-point guarantee more cheaply. We keep the explicit loop in the teaching version because it states the property: "the string I ship must survive being re-parsed as itself."
Q: Why forbid <template> and <noscript> rather than handle them?
A: Because "handle the special element correctly, forever, across every future browser" is a losing maintenance bet. Removing the element removes the special parsing context that made it exploitable. You only take on "handle it" for elements an app truly can't live without.
Q: Is this enough? Can I ship this?
A: This is a teaching sanitizer — ~90 lines, no CSS parser, no URL policy engine, no config surface. Ship DOMPurify or the native Sanitizer API. Use this to understand what those are doing and to audit a config. And read Module 11: even a perfect sanitizer is one layer.
