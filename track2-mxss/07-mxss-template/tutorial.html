<template> Reparentingthe fragment a sanitizer forgets

A <template>'s content is parsed into a separate, inert DocumentFragment. template.children is empty; the real content is template.content.children. A sanitizer that walks children sees nothing to clean — and when the app extracts that fragment into the live DOM, everything it skipped runs.

What this module proves

forgetfulSanitize('<template><img src=x onerror=alert(1)></template>') returns the payload with onerror intact, because it never descended into .content. Extract the template — live handler.

The Big Analogy

Some crates arrive at Sekondi marked <template> SAMPLE ONLY — NOT FOR SALE. The rule: don't inspect them, don't sort them — they're display samples, they never enter the market. Kofi logs the crate and moves on. He never opens it.

Weeks later the shop decides the sample is going on the shelf after all. Nobody re-runs it through customs — it was already logged. It goes straight to the floor, contents unchecked, because the one time it passed the officer, the officer was told not to look inside.

02

What Happens, Step by Step

  1. Attacker submits <template><img src=x onerror=alert(1)></template>.
  2. Parser: the <img> goes into template.content — a DocumentFragment hanging off the template, not in template.children and not in the document tree.
  3. Sanitizer walks node.children recursively. At the <template> it recurses into template.children — which is empty. It scrubs nothing. It emits the template unchanged.
  4. App does const t = box.querySelector('template'); target.innerHTML = t.innerHTML (or target.append(t.content)). The fragment's contents — <img onerror>, never touched — are now in the live document. XSS

07

Brain Exercise

The thorough sanitizer unwraps <template> rather than keeping it and cleaning its content. Why is unwrapping safer than cleaning-in-place?

Because a kept <template> re-introduces the exact gap on the next hop. If the sanitizer's output still contains <template>…clean content…</template>, and that output is later re-sanitised by a different (forgetful) sanitizer, or embedded in a page whose CSP/framework logic treats template content specially, or serialised and re-parsed in a context where template content model differs — the separate-fragment property is a liability again. Unwrapping collapses it to ordinary, fully-walked nodes with no special parsing context left to exploit. "Remove the thing that makes it special" beats "carefully handle the special thing" — the same principle as Module 8's forbidden-element list.

08

There Are No Dumb Questions

Q: Is this the same bug as declarative shadow DOM (<template shadowrootmode>)?
A: Same family, newer surface. DSD templates are attached as a shadow root during parsing — a sanitizer that doesn't handle shadowrootmode can leave a whole shadow tree unscrubbed. Forbid the attribute, or use a parser API that doesn't process DSD (the Sanitizer API — Module 11).
Q: Why does <template> even use a separate fragment?
A: So its content can hold otherwise-invalid combinations (a <tr> with no <table>, a bare <td>) without the parser "fixing" them, and so scripts/images/iframes inside don't run or load until the template is used. The inertness is the feature; skipping it during sanitisation is the bug.
Q: Does DOMParser put template content where I expect?
A: Yes — doc.querySelector('template').content is the fragment, in a DOMParser document just as in a live one. The trap is code that reads .innerHTML / .childNodes of the template and assumes that covers it.
