Track 1 · Module 02 · Build phase

Two Conditions,One Gate

This module extracts the single predicate the whole course orbits — flag enabled AND current node is table-family — and proves it against a real 2×2 truth table, before either half of that condition has any machinery behind it.

What this module proves

isFosterParentingTarget(state) returns true for exactly one of four (flag, current-node) combinations — flag ON and current node table-family — and false for the other three, including a stack-empty edge case that doesn't throw.

01

The Big Analogy

A door with an electronic lock that needs two separate signals to open — a keycard swipe AND a staff member's remote buzz-in — will not open for either one alone. Module 02 builds exactly that lock, and nothing else: no door mechanism yet (no relocation destination, Module 05), no wiring for when the buzzer signal turns on and off (Module 03's job). Just the lock's decision logic, tested by hand-feeding it every combination of "keycard swiped? yes/no" and "buzzer active? yes/no," confirming it only ever says "open" for exactly one of the four combinations.

02

What Happens, Step by Step

  1. FOSTER_PARENT_TARGETS is defined as a frozen Set of exactly five tag names: table, tbody, tfoot, thead, tr.
  2. isFosterParentingTarget(state) reads the current node off state.stack and checks two things: is state.fosterParentingEnabled truthy, and is the current node's tag name in the five-element set?
  3. The demo first runs a real Module 01 parse up to <table>, proving the predicate can be exercised against genuine engine state.
  4. It then runs all four (flag, tag) combinations by directly setting state.fosterParentingEnabled and swapping the top of the stack, and asserts the result matches [false, true, false, false] exactly.
  5. It separately tests an empty stack (no current node), asserting the predicate degrades to false rather than throwing.

04

The Code, Explained

The whole module, in one function:

function isFosterParentingTarget(state) {
  const target = state.stack[state.stack.length - 1];
  return (
    Boolean(state.fosterParentingEnabled) &&
    Boolean(target) &&
    FOSTER_PARENT_TARGETS.has(target.tagName)
  );
}

Note what's absent: no if (result) { relocate... }, no code that ever sets fosterParentingEnabled itself. This function only ever answers the yes/no question — see DECISIONS.md for why keeping it a pure predicate, with no side effects, is the central design decision of this module.

05

Limits — What You Cannot Do Yet

Can't do yet

  • Automatically turn fosterParentingEnabled on or off — it's set by hand in this module's demo
  • Actually relocate a node anywhere — no destination algorithm exists until Module 05
  • Reach a real <td> current node via the dispatch loop — "in cell" mode isn't implemented, so the demo swaps the stack directly instead

Can do

  • Correctly answer the gate question for any (flag, current node) combination, including the empty-stack edge case
  • Serve as the one predicate every later module's "should this fire?" check calls, unchanged

07

Brain Exercise

Prerequisite P3 asked you to restate condition 2 in terms of the stack: is it about the stack's contents, or specifically its top? Now that you've seen isFosterParentingTarget()'s source, what's the answer — and what would change if it were the other one?

It's specifically the top — state.stack[state.stack.length - 1], the current node, and nothing else. If it checked the stack's full contents instead (e.g. "is there a table-family element anywhere in the stack"), then Module 02's own demo would break: being deep inside a table but with current node <td> would incorrectly gate true, contradicting the attached reference course's own "Watch it" callout in its Module 02: "Being in a table is not the test... you can be deep inside a table and not foster (you're in a cell)." The empty-stack edge case this module tests only makes sense under the "top of stack" reading too — under a "contents" reading, an empty stack and a stack with no table-family member would be indistinguishable failure modes for a different reason.

08

There Are No Dumb Questions

Why is the demo's truth table only 4 rows plus 1 edge case, instead of testing all five table-family tag names individually?

Because isFosterParentingTarget() doesn't distinguish between the five — it only asks Set membership, which is a single code path regardless of which of the five matched. Testing table and td (a representative "yes" and a representative "no") exercises that code path completely; testing all five would be five assertions with zero additional branch coverage. Track 1 Module 04 ("why exactly five elements") is where the five get tested individually — there, the point is to examine each one.

The predicate reads state.fosterParentingEnabled, but nothing in this module ever sets it during real parsing — only the demo does, by hand. Doesn't that mean the gate is currently dead code?

Within this module alone, yes — and that's intentional, not an oversight. Module 02's whole purpose is to build and verify the gate's logic in isolation, before Module 03 wires up the only real trigger for the flag (the "in table" mode's anything-else clause) and before Module 05 gives a true "gate open" event anywhere to go. Each module proves one thing; "is this predicate correct" and "is this predicate ever called for real" are different claims, proven in different modules.

Why Boolean(state.fosterParentingEnabled) instead of just state.fosterParentingEnabled directly in the && chain?

Cosmetic, not functional — JavaScript's && would short-circuit correctly either way. It's here so the function's return value is guaranteed to be a real boolean (true/false) rather than possibly returning undefined (if fosterParentingEnabled was never set) or the target object itself. Given this predicate is asserted against with assert.deepEqual(results, [false, true, false, false], ...), a stray undefined instead of false would fail that assertion — better to make the contract explicit in the source than rely on the test to paper over it.

09

What's Next

Module 03 gives fosterParentingEnabled the real lifecycle it doesn't have yet: wired into the dispatch loop's actual in table "anything else" clause, turned on immediately before one token is processed under in body's rules, and turned back off immediately after — never surviving past the single token that raised it. The truth table this module proved stays exactly the same; Module 03's job is only to make the flag's left-hand column (ON/OFF) something the engine decides automatically, instead of something the demo sets by hand.
