Track 1 · Module 07 · Build phase

What Refusesto Be Fostered

Five token shapes reach in table and never make it to the anything-else fallback at all. This module builds all five — and one deliberate near-miss that does reach the fallback, producing a real, well-documented bug.

What this module proves

<table><form><input name=x></form></table> produces a permanently empty <form> and an <input> fostered clean outside the table — the exact tree shape behind a real, commonly-reported "why is my form empty" bug.

01

The Big Analogy

Not every unexpected arrival gets walked to the gate. Some have their own standing instructions posted right at the door: the mail (<style>/<script>) gets set on the front table without question. A courier with a hidden-delivery slip (<input type=hidden>) drops the package and leaves immediately — nobody escorts them anywhere, they just weren't staying. A visiting official with a clipboard (<form>) checks in, gets logged, and is shown straight back out — before anyone they were supposed to bring in with them even reaches the door.

That last one is the trap: the official's own guest (a following <input>) arrives after the official has already left, finds no escort waiting, and gets walked to the gate like anyone else unexpected.

02

What Happens, Step by Step

  1. inTableRefusesFostering(token, state) checks, in order: is this <style>/<script>/<template> (start or end tag)? A hidden <input>? A <form>? A comment? A DOCTYPE?
  2. Each matched case is inserted (or, for DOCTYPE, simply ignored) and the function returns true — signaling "handled, do not foster."
  3. An <input> whose type is anything other than hidden — including no type at all — is explicitly left unmatched, returning false.
  4. dispatch7 checks this function FIRST, before Module 05's <td>/<th>/<tr> rules and before the anything-else/foster-parenting fallback.
  5. For the childless-form case: <form> is inserted then immediately popped. The current node reverts to table right away — so the very next token, the nested <input>, is evaluated against a table-family current node, and (having no type=hidden) falls straight through to fostering.
03

A Map of This Module's State

Input — visually, input LOOKS like it's inside form 
<table><form><input name=x></form></table>
Output — it never was 
body
├─ input   ← fostered, NOT inside form
└─ table
   └─ form   ← permanently empty

Nothing in the source markup looks wrong. The bug is entirely in when form stops being the current node — one token before its own child ever arrives.

04

The Code, Explained

The two lines that create the trap:

if (token.type === 'StartTag' && token.tagName === 'form') {
  insertHtmlElement(state, token.tagName, token.attrs);
  state.stack.pop(); // childless, permanently
  return true;
}

And the branch that makes the trap spring — note it's the ONE case in this whole function that returns false:

if (token.type === 'StartTag' && token.tagName === 'input') {
  const type = (token.attrs.get('type') || '').toLowerCase();
  if (type === 'hidden') { /* ...pop, return true... */ }
  return false; // any other type, or none: falls through to fostering
}

Full rationale for every branch, plus why <style>'s content tokenizing correctly here is a coincidence of the test input rather than a general guarantee, is in DECISIONS.md.

Limits — What You Cannot Do Yet

Can't do yet

  • Tokenize <style>/<script> content correctly if it contains a literal < — no RAWTEXT tokenizer state
  • Reject a second nested <form> — no form element pointer modeled
  • Represent form-association in the DOM sense — ElementNode has no such field

Can do

  • Correctly intercept five distinct token shapes before the fostering fallback ever sees them
  • Reproduce the exact tree shape of the childless-form bug, byte-for-byte against a real browser

07

Brain Exercise

Of the five things this module handles specially, exactly one — the ordinary (non-hidden) <input> — is defined by inTableRefusesFostering returning false. Why does that one case matter more to this module's overall point than the four that return true?

Because a module titled "what refuses to be fostered" that only ever showed things being refused would leave the boundary of that refusal invisible. The one false case is what proves the other four aren't refusing fostering by some blanket "anything inside <form> or near <input> is safe" rule — they're refusing it for five completely independent, specific reasons, and stepping one tag outside any of those five reasons (a plain <input>, or an <input> that arrives after its guardian <form> already left) drops straight back into the ordinary fostering behavior every module since 02 has been building. The childless-form bug only exists because that boundary is real and sharp, not fuzzy.

08

There Are No Dumb Questions

Is the childless-form bug this module reproduces an engine limitation, or genuine browser behavior?

Genuine browser behavior — verified directly against a real browser's DOMParser before this engine was tested against the same input (see DECISIONS.md and the module's real-output comparison). This isn't a case where our simplified engine diverges from a real parser; it's a case where our simplified engine correctly reproduces a widely-encountered, real-world parsing quirk. The attached reference course calls it "the parser's single most reliable source of 'why is my form empty' bug reports" for exactly this reason.

Why does inTableRefusesFostering check type case-insensitively (.toLowerCase()) but nothing else in this module bothers with case normalization?

Because that specific case-insensitivity is called out explicitly in the real spec's wording for this exact clause — the attached reference course's own containment table states it as "ASCII-case-insensitively matching hidden." Tag names elsewhere in this engine are already lowercased by the tokenizer itself (Module 01's tokenizer.js lowercases every tag name it emits), so no other comparison in this file needs its own normalization — this one is different because it's comparing an attribute value, which the tokenizer has no reason to touch.

Why test the DOCTYPE-mid-table case by calling inTableRefusesFostering directly instead of running it through the real tokenizer and full engine like every other case in this module?

Because a second DOCTYPE appearing partway through a document is markup no realistic input produces — constructing a full, tokenizable HTML string containing one would test this engine's tokenizer's DOCTYPE-anywhere behavior more than it would test this module's actual claim (that the token, once produced, is correctly ignored). Calling the function directly with a hand-built token isolates exactly the thing being proven, the same technique Module 02's truth table and Module 04's atlas both used for similar reasons.

What's Next

Module 08 returns to character tokens — but not one at a time. It builds "in table text" mode: the buffered-run, all-or-nothing decision that determines whether a stretch of whitespace-heavy text stays inside the table or gets fostered out along with a single non-whitespace character hiding among it. It's the module that finally explains why this course's engine emits one character token per character (Prerequisite P1) instead of batching them — Module 08 is where that granularity actually gets used for something.
