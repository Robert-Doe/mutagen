Track 1 · Module 00 · Build phase

Tokens &Node Shape

Before a parser can decide where anything goes, it needs something to hold what it decides. This module builds the two data structures — tokens in, DOM nodes out — that every later module reads and writes.

What this module proves

A hand-authored token stream for a small, ordinary (non-table) fragment can be represented exactly by tokens.js, and the DOM it describes can be built and rendered exactly by nodes.js — including the character-fusion behavior Module 09 will later depend on.

01

The Big Analogy

Imagine a factory with two rooms. In the first room, an inspector walks along a conveyor belt of raw material and tags each piece with a label: "this is a doorframe," "this is a hinge," "this is a screw." That's the tokenizer — it never assembles anything, it just identifies and labels.

In the second room, an assembler takes those labeled pieces one at a time and decides where each one gets bolted onto the structure being built. That's tree construction, starting in Module 01.

This module builds neither room's machinery yet. It builds the shapes of the labels (tokens.js) and the shape of the structure being assembled (nodes.js) — the raw materials both rooms will pass back and forth. Get these two shapes wrong, and nothing built downstream can be trusted, no matter how correct the assembly logic is.

02

What Happens, Step by Step

  1. tokens.js defines six factory functions, one per token shape from P1: doctypeToken, startTagToken, endTagToken, commentToken, characterToken, eofToken.
  2. characterToken() is given a runtime guard: call it with anything other than a single character and it throws, rather than silently accepting a batched string.
  3. nodes.js defines four classes, one per node kind from P2: DocumentNode, ElementNode, TextNode, CommentNode.
  4. insertNode(parent, node, index) centralizes the one splice operation every future "insert a ___" algorithm will call.
  5. tryFuseCharacter(parent, data, index) checks whether the node immediately before the insertion point is already a TextNode, and if so appends to it instead of creating a new one.
  6. test/demo.js hand-authors a token stream for <div class="a"><p>hi <b>there</b></p></div>, builds the corresponding node tree using only these primitives, renders it, and asserts the result is exactly right.

04

The Code, Explained

The single-character guard on characterToken() — this is the line most likely to look like overkill until Module 08:

function characterToken(data) {
  if (data.length !== 1) {
    throw new RangeError(
      `characterToken() takes exactly one character, got ${JSON.stringify(data)} ` +
      `(length ${data.length}). The tokenizer never batches characters into a token — ` +
      'see prerequisites/prereq_tokens.html and Track 1 Module 08.'
    );
  }
  return { type: 'Character', data };
}

And the fusion check that test/demo.js calls before every character insertion:

function tryFuseCharacter(parent, data, index = parent.children.length) {
  const before = parent.children[index - 1];
  if (before instanceof TextNode) {
    before.data += data;
    return true;
  }
  return false;
}

Full rationale for every choice in both files — including why tokens are plain objects but nodes are classes, and why attrs is a Map — is in this module's DECISIONS.md.

05

Limits — What You Cannot Do Yet

Can't do yet

  • Parse a real HTML string — there's no tokenizer, only hand-authored token arrays
  • Automatically decide where a node goes — insertNode() takes the location as an argument, it doesn't compute one
  • Track which element is "current" — no stack of open elements exists yet
  • Reproduce foster parenting, or any insertion-mode behavior — that starts Module 02

Can do

  • Represent any token or node this course's engine will ever need
  • Splice a node into a parent at an arbitrary position
  • Fuse adjacent character insertions into one TextNode
  • Render a subtree as the same ASCII diagram format used in every tutorial

07

Brain Exercise

insertNode() takes an explicit index parameter instead of always appending. Nothing in this module's demo ever passes a non-default index. Why build that flexibility in now, before any module needs it?

Because Module 05 (the seven substeps of foster parenting) computes an adjusted insertion location that is very often not "after the last child" — it's "immediately before a specific existing sibling." If insertNode() could only append, Module 05 would have to reach past it and manipulate .children directly, defeating the whole point of centralizing the splice operation (see DECISIONS.md). This isn't speculative scope creep — it's the one piece of flexibility a concrete, already-scoped future module (05) is known to need, added at the layer where it's cheap, not invented for a "maybe."

08

There Are No Dumb Questions

Why does nodes.js use ES classes but tokens.js uses plain object factory functions? Isn't that inconsistent?

It looks inconsistent until you compare lifecycles. A token is created, read once by tree construction, and thrown away — nothing about it ever needs to change, and nothing ever needs to ask "is this the same token as that one?" A node, by contrast, gets pushed onto the stack of open elements, popped, and — per the spec's own explicit warning (Prerequisite P3) — can still be mutated afterward through a stale reference. That needs stable identity and mutable state, which is what a class gives you and a plain object doesn't cleanly support. Different lifecycles, deliberately different representations.

Why not just use the real DOM API (document.createElement, etc.) instead of writing our own node classes?

Two reasons. First, this is a build-it-yourself course — using the browser's own tree construction to build a tree construction engine would prove nothing. Second, our nodes intentionally expose internals (a raw, mutable .parent pointer; a plain .children array you can splice directly) that the real DOM API deliberately hides behind methods like appendChild. Module 05 needs to insert a node before a specific sibling that isn't necessarily the parent it's philosophically "inside" — easier to reason about with raw access than through DOM's own insertion methods.

Attributes are stored as a Map. Why not just use a plain JavaScript object, like { class: "a" }?

An attacker-influenced attribute name like __proto__ collides with JavaScript's own prototype chain when used as a plain-object key, which is exactly the kind of subtle bug this course's Track 2 (mXSS) module cares about. Map has no such collision surface, and its API (.get/.set/.entries()) matches how the spec itself talks about an attribute list — as an ordered map.

The demo's assertions check exact string equality against a hardcoded expected tree. Isn't that brittle?

For this module, brittleness is the point. Module 00 exists to prove the data structures are correct for one concrete case, not to be a general-purpose test suite — later modules (05, 06, 10) add many more cases, each similarly asserted exactly, because "roughly right" tree shapes are exactly how foster-parenting bugs hide (see Module 07's "Watch it" callout later in the course, on the childless-form bug). Exact assertions now build the habit the whole course runs on.

What's Next

Module 01 builds the piece this module deliberately left out: the stack of open elements (Prerequisite P3) as a live, mutating structure, plus a minimal insertion-mode dispatch loop that can drive the "in body" rules far enough to reach a <table> start tag for the first time. Nothing in Module 01 triggers foster parenting yet — that's still two modules away — but it's the first module where tokens actually get consumed automatically instead of hand-walked, which is the whole reason today's data structures needed to be right before we could trust anything built on top of them.
