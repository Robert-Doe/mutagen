Scope &Why Table Is a Wall

The mechanism that stops end tags from reaching across container boundaries — and, seen from the other direction, the same underlying fact Module 04 already proved: table/td/th are structural walls, whether content is trying to get IN (fostering) or an end tag is trying to reach OUT (scope).

What this module proves

A stray </div> inside a <td>, closing an element opened outside the table, is silently ignored — verified end to end through the complete engine, and separately proven as a direct consequence of the scope algorithm itself.

01

The Big Analogy

A guest holding a room key from the east wing wanders into the west wing and tries to use it on a door there. It doesn't work — not because anyone stops them, but because the key was never valid past the wing boundary to begin with. Scope is that boundary check: an end tag is a key, and certain rooms (table, td, th, and a handful of others) are wing boundaries no key from outside can cross, no matter how the hallways wind between them.

02

What Happens, Step by Step

  1. hasElementInScope(state, target, scopeList) walks the stack from the current node downward. Target found first → true. A scope-list member found first → false, stop.
  2. Four named variants wrap this with different scope lists: hasInScope (the base list), hasInListItemScope (base + ol/ul), hasInButtonScope (base + button), hasInTableScope (a much narrower list: only html/table/template).
  3. The generic EndTag branch now checks hasInScope first. Not in scope → silently ignored, no pop, no error surfaced.
  4. In scope AND current node matches exactly → pops, exactly as every module since 05.

04

The Code, Explained

The entire mechanism, in the branch where it matters:

if (token.type === 'EndTag') {
  if (!hasInScope(state, token.tagName)) {
    return; // parse error — ignore. This is "table is a wall" in one line.
  }
  const cur = currentNode(state);
  if (cur && cur.tagName === token.tagName) {
    state.stack.pop();
    /* ... */
  }
}

And the scope check itself — note the target is checked before the boundary, which is what lets a scope list find itself as a target (Case: does table exist to close, checked FROM inside the table):

function hasElementInScope(state, targetTagName, scopeList) {
  for (let i = state.stack.length - 1; i >= 0; i--) {
    const tagName = state.stack[i].tagName;
    if (tagName === targetTagName) return true;   // checked FIRST
    if (scopeList.has(tagName)) return false;    // boundary, checked second
  }
  return false;
}

07

Brain Exercise — the Track 1 review lab

Twelve markup snippets, drawn from this course's own build history. Predict the output before revealing — every one of these was verified against a real browser somewhere in Modules 05–13.

1. <div>abc<table>def</table></div> — how many Text nodes end up under div?

One. #text "abcdef", fused. Module 05, Module 09.

2. <table><td><table><tr>FOO</table></table> — inside or outside a table, overall?

Inside the outer table's <td> — one hop out of the nearest table is not one hop out of all tables. Module 05.

3. <table><math></math></table> — inside or outside the table?

Outside — foreign elements foster exactly like HTML elements (the corrected 2013 spec text). Module 06.

4. <table><form><input name=x></form></table> — does <input> end up inside <form>?

No. <form> is popped the instant it's created; <input> arrives with current node already back to table, and fosters outside it entirely. Module 07's childless-form bug.

5. <table> </table> (whitespace only) — parse error?

No parse error. Whitespace-only runs insert inside the table normally. Module 08.

6. <table> x </table> (one non-space character) — where does the whitespace around x go?

Travels with it — the whole buffered run fosters together, fused into one text node. Module 08.

7. <table><b><tr><td>aaa</td></tr>bbb</table>ccc — how many <b> elements, total?

Three — distinct objects, verified by identity, not just by matching output. Module 10, the spec's own canonical example.

8. table.innerHTML = '<p>x</p>' vs. parsing <table><p>x</p></table> as a document — same result?

Opposite. innerHTML: p INSIDE. Document parse: p OUTSIDE. Module 11 — "where does a <p> in a table end up" has no answer until you say how it got there.

9. <table><template><p>a</p></template></table> — does the <p> get fostered before the table?

No — it's intercepted into the template's own .content, never reaching the main tree at all. Module 11.

10. Second <html foo="1">... later, <html foo="2" bar="3"> — final attributes on the one <html> element?

foo="1" bar="3" — first occurrence wins for duplicates, new attribute names get added. Module 12.

11. <div><table><tr><td></div></td></tr></table></div> — does the stray </div> close anything?

No — div isn't in scope past the <td> boundary; the end tag is silently ignored. This module, Part 1.

12. Hardest — combine two rules: <table><template><tbody>FOO</template></table> — where does FOO land?

Inside the template's .content, as <tbody>'s sibling — substep 1 (the template check) fires before the ordinary "before nearest table" computation ever runs, because a <template> deeper on the stack than the last table intercepts first. Module 11.

08

There Are No Dumb Questions

Is "table is a wall" (scope) the same mechanism as foster parenting, just running in the opposite direction?

No — related, but genuinely separate mechanisms that happen to share the same structural elements as their walls. Foster parenting is about WHERE AN INSERTION LANDS (Module 05's adjusted insertion location). Scope is about WHETHER AN END TAG IS EVEN ALLOWED TO ACT (this module). They're both gated by `table`/`td`/`th`-family elements because those elements are structurally special in the same underlying way (Module 04's "no box to host a stray node" reasoning) — but the two algorithms don't call each other, share code, or run at the same point in tree construction.

Why does scope check the CURRENT node's tag first as a possible match, rather than starting the search one level below it?

Because the current node is a completely valid answer to "is there a target element open right now" — the classic use is closing the element you're literally inside of (e.g. </p> while current node is exactly p). Starting one level down would make the single most common case — closing the thing you're directly inside — require special-casing instead of falling out of the general algorithm for free.
