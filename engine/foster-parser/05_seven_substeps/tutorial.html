The SevenSubsteps

Every module so far proved whether foster parenting fires. This module proves where the node actually goes — and for the first time, checks the answer against a real browser's DOMParser, not just this engine's own internal consistency.

What this module proves

For <div>abc<table>def</table></div> and the nested-table case <table><td><table><tr>FOO</table></table>, this engine's output matches a real browser's DOMParser output byte-for-byte.

01

The Big Analogy

Security doesn't leave you in the hallway. Not outside the row, not outside the section. They walk you past every corridor, out the front gate of the nearest estate you're currently inside, and stand you on the pavement immediately to its left — the last position before that estate begins.

Which estate? Whichever one you're standing in right now. If that estate happens to sit inside a room of a larger estate, you get put on that room's floor — you've left one table, but you haven't necessarily left tables altogether. That's the nested-table case this module's second test proves: FOO gets walked out of the inner table and placed on the outer table's <td> floor — still very much inside a table overall.

02

What Happens, Step by Step

  1. getAdjustedInsertionLocation(state) checks Module 02's gate first. If it's false, return "current node, after last child" — exactly Module 01's original behavior.
  2. If the gate is true, find the last <table> on the stack of open elements, scanning from the current node upward.
  3. No table found at all → the fragment case (substep 4): insert inside the very first element on the stack.
  4. That table has a parent node → the normal case (substep 5): insert inside that parent, immediately before the table.
  5. That table has no parent (removed/moved mid-parse) → substeps 6–7: insert inside whatever element is immediately above the table on the stack.
  6. insertCharacterAtAppropriatePlace/insertElementAtAppropriatePlace call this algorithm and splice into whatever it returns — text still fuses with an existing sibling TextNode at that location, exactly as Module 00's tryFuseCharacter already implemented.

"Last table" means nearest, not outermost — substep 2 finds the inner table first, because the stack is scanned from the current node upward, not from the bottom down.

04

The Code, Explained

The whole algorithm, steps 2 through 7 collapsed into one function:

function getAdjustedInsertionLocation(state) {
  const target = state.stack[state.stack.length - 1];
  if (!isFosterParentingTarget(state)) {
    return { parent: target, index: target.children.length };  // step 3
  }
  // ...find lastTableIndex by scanning the stack from the top...
  if (lastTableIndex === -1) {
    return { parent: stack[0], index: stack[0].children.length };  // substep 4
  }
  const lastTable = stack[lastTableIndex];
  if (lastTable.parent) {
    return { parent: lastTable.parent, index: lastTable.parent.children.indexOf(lastTable) };  // substep 5
  }
  return { parent: stack[lastTableIndex - 1], index: stack[lastTableIndex - 1].children.length };  // substeps 6-7
}

Note step 3's fallback is byte-identical in effect to Module 01's original hardcoded insertion — that equivalence is what makes it safe to route every insertion through this one function from now on, foster-parenting or not. Full rationale, including why this module can't simply reuse Module 01's MODES['in body'] the way Module 03 did, is in DECISIONS.md.

05

Limits — What You Cannot Do Yet

Can't do yet

  • Redirect into a <template>'s contents (substeps 1, 3) — no DocumentFragment node kind until Module 11
  • Verify the detached-table case (substeps 6–7) against a real browser — requires script-interleaved parsing, out of scope entirely
  • Close a table properly with </table> when the current node is several levels deeper (e.g. inside a <tr>) — needs "generate implied end tags," not yet built

Can do

  • Compute the exact same insertion point a real browser computes, for both a simple fusion case and a nested-table case
  • Correctly fuse fostered text across an inserted element boundary (the abc+def → abcdef case)
  • Foster from a <tr> while correctly not fostering from a <td>, inside the same real parse

Getting a blank or broken result?

If Case 2's output shows #text "FOO" nested inside the inner <tr> instead of inside the outer <td>, the stack scan in getAdjustedInsertionLocation is finding the wrong "last table" — check it scans from the top of the stack downward, not the bottom up, so it finds the nearest table, not the outermost.

07

Brain Exercise

This module's DECISIONS.md admits substeps 6–7 (the detached-table case) are implemented but never verified against a real browser. Given that, what exactly does this module's test suite actually establish about those two substeps — and what would it take to establish more?

It establishes only that the code doesn't crash and produces some defined, internally-consistent answer for a hand-constructed state where a table element has no parent — nothing about whether that answer matches what a real browser's parser would do when a <script> actually calls table.remove() mid-parse. To establish more, you'd need an engine capable of incremental, script-interleaved parsing (running a real JS engine's DOM mutation calls between tokens) — a fundamentally different, much larger undertaking than this course's static-string parser, and explicitly out of scope per ROADMAP.md. This is a good example of the difference between "the code runs without error" and "the code is verified" — this course tries hard to only claim the second when it's actually earned.

08

There Are No Dumb Questions

Why does this module bother implementing the fragment case (substep 4) and the detached-table case (substeps 6–7) at all, if neither is reachable by this engine's real parsing yet?

Because "appropriate place for inserting a node" is one algorithm with five branches in the real spec, and implementing four of five would leave getAdjustedInsertionLocation silently wrong (or crashing) for inputs a later module — Module 11, specifically — will need to exercise for real. Writing the whole algorithm now, with honest annotations about which branches are browser-verified versus only self-consistent, means Module 11 extends this file instead of rewriting it.

The demo compares strings that include indentation and exact formatting. Isn't that a fragile way to test a tree structure — wouldn't a structural/recursive comparison be more robust?

It's deliberately the more rigid choice, not an oversight. A structural comparison (e.g. walking both trees recursively and comparing node-by-node) could theoretically pass while still hiding a formatting or ordering bug that a byte-for-byte string comparison would catch immediately. Since the entire point of this module is "does this match a real browser, exactly" — not "does this roughly resemble a real browser" — the strictest available check is the right one, consistent with Module 00's FAQ answer about why its own assertions are exact rather than approximate.

Case 2 stops partway through — at the inner </table> — rather than finishing the whole input. Why is that an acceptable place to call this module's proof complete?

Because everything left unprocessed after that point only removes elements from the stack (three more end tags: the remaining </table>, and the implied </body>/</html>) — none of it inserts anything new. The tree this module compares against a real browser is therefore already in its final, complete shape by the time the engine hits a boundary it doesn't yet handle. DECISIONS.md states this reasoning explicitly rather than leaving it implicit, since "the test passed" and "the test proved what it claims to prove" are different questions worth answering separately.

What's Next

Module 06 proves this same getAdjustedInsertionLocation call isn't just for HTML elements and characters — foreign elements (SVG/MathML) and formatting elements reconstructed by the (not-yet-built) active-formatting-elements algorithm both route through the exact same function, unchanged.
