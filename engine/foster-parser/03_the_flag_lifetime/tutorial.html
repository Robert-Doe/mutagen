Track 1 · Module 03 · Build phase

The FlagLifetime

Module 02 built a lock that needs two signals. This module builds the only wiring in the entire engine that ever sends the second signal — and proves it fires for exactly one token, whether or not that token succeeds.

What this module proves

Enable → process one token → disable, unconditionally, via try/finally — and a subtle spec distinction most implementations get wrong on the first try: "process using the rules for in body" does not mean "switch to in body mode."

01

The Big Analogy

Picture a security guard who is not stationed anywhere — he's summoned by exactly one supervisor, for exactly one visitor, and then sent home. He doesn't relocate to a different post and stay there; he borrows a moment of the front desk's procedure manual, applies it to this one visitor, and leaves the front desk's normal staffing completely unaffected once he's done.

The tempting mistake is to imagine the guard becomes front-desk staff for a while — walks over, sits down, works the desk. That's not what happens. He reads their manual on the spot, standing where he already was, and — critically — the desk's own manual can still tell him to relocate somewhere else entirely (that's the <table> case: in body's own rule for a nested table explicitly says "switch to in table," and that instruction is still obeyed). Otherwise, when he's done, nothing about where anyone is stationed has changed.

02

What Happens, Step by Step

  1. The dispatch loop reaches in table mode with a token in hand that has no specific in table rule yet (every token, for now — Module 03 only implements the fallback).
  2. inTableAnythingElse() sets state.fosterParentingEnabled = true and logs 'enable'.
  3. It calls MODES['in body'](token, state) directly — not by setting state.mode and going through dispatch().
  4. Whatever in body's rule for that specific token does, happens: insert a character, insert a table and switch modes, or throw NotImplementedYet if in body has no rule either.
  5. Regardless of which of those three happened, a finally block sets state.fosterParentingEnabled = false and logs 'disable'.
  6. If step 4 threw, the error propagates onward after step 5 completes — the flag's cleanup and the error's visibility are independent guarantees.
03

A Map of This Module's State

Scenario A: fallback token in body can't handle either

mode: in table
  │
  ├─ enable  (flag → true)
  ├─ MODES['in body'](EndTag table)
  │     └─ throws NotImplementedYet
  ├─ disable (flag → false)   ← finally, runs anyway
  └─ error re-thrown

mode after: still "in table"

Scenario B: fallback token in body handles fine

mode: in table
  │
  ├─ enable  (flag → true)
  ├─ MODES['in body'](Character ' ')
  │     └─ inserts text, returns normally
  ├─ disable (flag → false)
  └─ no error

mode after: still "in table"

Same bracketing, same outcome for the flag, in both scenarios — only whether an error surfaces afterward differs. Mode never moves in either case, because neither token's in-body rule contains an explicit mode switch.

04

The Code, Explained

The line that makes the whole module correct — calling the rule table directly instead of routing through state.mode:

function inTableAnythingElse(token, state, log = () => {}) {
  log('enable');
  state.fosterParentingEnabled = true;
  try {
    MODES['in body'](token, state);
  } finally {
    log('disable');
    state.fosterParentingEnabled = false;
  }
}

Compare to the naive version this module's DECISIONS.md explains in detail — state.mode = 'in body'; dispatch(token, state); — which looks almost identical but silently overwrites the mode variable even when in body's own rule for that token never asked for a switch.

05

Limits — What You Cannot Do Yet

Can't do yet

  • Handle any in table-specific tag (<tr>, <td>, <caption>, …) — every token still falls to the anything-else fallback
  • Actually relocate a fostered node anywhere — the flag turns on and off correctly, but nothing yet reads it to change where an insertion happens (that's Module 05)

Can do

  • Correctly bracket the flag around exactly one token, on both success and failure paths
  • Preserve state.mode exactly as the spec's "process using the rules for X" technique requires, distinct from a real mode switch

Getting a blank or broken result?

If Scenario B's "mode after" prints in body instead of in table, you've reintroduced the naive state.mode = 'in body' approach — check that inTableAnythingElse() calls MODES['in body'](token, state) directly rather than setting state.mode first. If MODES is not defined, confirm Module 01's dispatch.js still exports it (see DECISIONS.md's note on this module's one additive edit to an earlier module's file).

07

Brain Exercise

Suppose a future module's in table-specific rule for <tr> needs to run before the anything-else fallback in this module. Where would that rule need to be checked, relative to inTableAnythingElse() — inside it, or before it's ever called?

Before it's ever called. inTableAnythingElse() is specifically the anything-else clause — by definition, the fallback for tokens no more specific rule claimed first. A future module's dispatch wrapper needs to check "is this token one of the specific cases (<tr>, <td>, etc.)?" first, and only call into this module's fallback if none matched — mirroring exactly how the real spec's "in table" section lists specific-tag rules first and ends with "anything else" last. This module's function is deliberately named to make that ordering obvious to whoever extends it next.

08

There Are No Dumb Questions

Why does Scenario A bother re-throwing the error at all? Wouldn't it be simpler for the wrapper to just swallow it, since the flag got cleaned up successfully either way?

Because "the flag got cleaned up" and "the token got handled" are two completely different claims, and conflating them would hide real bugs. If inTableAnythingElse() swallowed the error, a caller would have no way to know that </table> wasn't actually processed — the parse would silently continue as if everything were fine, which is exactly the "roughly right tree shapes are how foster-parenting bugs hide" failure mode this course has flagged since Module 00's FAQ.

This module exports MODES from Module 01's file. Doesn't that break the "every module only adds, never edits" rule from Module 02's DECISIONS.md?

It bends it, deliberately and narrowly, and DECISIONS.md says so explicitly. The rule's spirit is "don't change what already works," not "never touch an earlier file's text." Adding an export doesn't change any existing behavior — Modules 00, 01, and 02's own tests were re-run after this change specifically to confirm that, and all three still pass unmodified. The alternative (copy-pasting in body's rule table into Module 03) would violate a stronger principle: one source of truth per rule table.

Why use a finally block instead of just writing the disable line twice — once after a successful call, once in a catch?

Because that duplicates the exact line whose entire job is "always run this, no matter what" — which is a description of what finally means, built into the language, rather than something to hand-maintain in two places that could drift apart. It's also the more direct translation of the spec's own phrasing: "enable, process, disable" reads as one guaranteed sequence, and try { process } finally { disable } says exactly that in code.
