The AdoptionAgency Algorithm

The spec's repair machinery for misnested formatting elements — <b><i>x</b>y</i>-shaped input — built and verified for real this time, after Module 10 drew a line around it and called it out of scope. This module exists specifically to answer a question every prior module dodged: what does the parser actually do when the HTML is wrong?

What this module proves

Browsers never reject malformed HTML. There is no such thing as an HTML syntax error a browser refuses to render. <b><i>x</b>y</i> — a document where the tags don't nest, which by XML's rules isn't even well-formed — produces a specific, deterministic, spec-mandated tree, the same tree in every conformant browser, built by exactly this algorithm.

01

The Big Analogy

Two wristbands, put on in one order — <b>, then <i> — someone tries to take them off in the other order: </b> arrives first. You can't just cut the outer band; the inner one is looped through it. The adoption agency algorithm is the security guard's actual procedure for this exact tangle: find where the crossing happened, decide how much needs to be cut and re-tied, and re-issue new bands in a shape that makes sense — without ever just refusing to let the person leave. That last part is the whole point of this module. A real browser has no "reject and stop" button. Whatever bytes arrive, however tangled, it must produce some tree, and — since 2008 — a tree every other browser produces too.

Why this is a bigger deal than it sounds

Before the WHATWG HTML5 effort (roughly 2004–2008), "what does a browser do with broken HTML" had no single answer — it had one answer per browser, sometimes per browser version, reverse-engineered by trial and error by anyone who needed to match it. The same malformed markup could render as three different trees in three different browsers, and site authors learned to write markup that "happened to work" in whichever browser they tested against — a major, quietly-load-bearing source of real interoperability bugs for over a decade. Ian Hickson's HTML5 tree-construction algorithm — including this one, its single most intricate piece — is a from-scratch, exhaustive specification of exactly how to recover from every class of malformed input, written by studying what browsers already did and forcing convergence on one answer. It is not a "nice to have" cleanup pass. It is the reason "view source" on almost any real website — full of unclosed tags, misordered elements, and decades of copy-pasted markup — renders identically everywhere at all.

02

What Happens, Step by Step — Reading Malformed Input

Walk <b>1<i>2</b>3</i>4 — Case 1 below — through the algorithm exactly as the parser does. This is "how the parser handles malformed HTML," made concrete:

  1. The tag-nesting violation itself. By the time </b> arrives, the stack is html > body > b > i — <i> opened after <b> and is still open. </b> does not match the current node (i). This is the malformed shape: an end tag whose start tag is buried, not on top.
  2. Find the formatting element. Search the active formatting elements list, back to front, for an entry named b. Found — this confirms a <b> really is open somewhere, not just missing entirely (a separate, unrelated kind of "wrong").
  3. Is it actually reachable, in scope? If the search hit a scope boundary first (Module 13), the end tag is simply ignored — a different, much cheaper recovery than anything this module builds. Not the case here.
  4. Look for a furthest block — a "special category" element (Module 14's own new list: div, table, p, and dozens more) sitting above b on the stack. In this case: none. i is a formatting element too, not special-category.
  5. No furthest block found → the cheap path. Pop everything down to and including b, drop it from the active formatting list, done. No cloning, no relocation — the "untangling" turned out to be a plain pop once the actual stack shape was checked. This is the single most common misconception about this algorithm: the textbook <b>/<i> overlap almost everyone uses to introduce it doesn't exercise the famous cloning machinery at all.

Case 2 (a <div> misnested inside <b>) hits step 4 differently: div is special-category, so a furthest block is found, and the full clone-and-relocate machinery — steps 5 onward, the "outer loop"/"inner loop" the spec names — actually runs. That's what makes this the hardest recovery algorithm in the spec: most malformed input takes the cheap exit; only genuinely tangled structural misnesting reaches the expensive one.

03

A Map of This Module's State

Input — a <div> misnested inside a <b>, itself misnested inside another <div> 
<div id="outer"><b>bold<div id="inner">block</b>after</div>more</div>
Output — real browser DOMParser, verified twice against a parentElement-labeled serializer 
body
└─ div#outer
   ├─ b
   │  └─ #text "bold"          ← the ORIGINAL <b>, left behind on the outside
   ├─ div#inner
   │  ├─ b
   │  │  └─ #text "block"      ← a CLONE of <b>, carrying div#inner's own content
   │  └─ #text "after"
   └─ #text "more"

Two distinct <b> elements exist in the final tree — not one element magically present in two places, not a parse error that just drops the tag. The original stays wrapped around "bold"; a brand-new clone gets built and threaded around "block", inside div#inner, on the far side of the misnesting. This is the algorithm's whole purpose in one picture: turn markup where a formatting tag's start and end straddle a structural boundary into a tree where formatting is applied on both sides of that boundary, correctly, by duplicating the formatting element rather than moving it whole.

04

The Code, Explained

The "cheap path" from Section 02 — most malformed input never leaves this branch:

if (!furthestBlock) {
  log('no-furthest-block');
  while (state.stack.length && state.stack[state.stack.length - 1] !== formattingElement) {
    state.stack.pop();
  }
  state.stack.pop();               // pop the formatting element itself
  const idx = list.indexOf(formattingElement);
  if (idx !== -1) list.splice(idx, 1);
  return;
}

The expensive path's most important single line — the one this module's build got wrong on the first attempt, verified against parse5's real source rather than a too-literal reading of spec prose (see DECISIONS.md for the full corrective story):

state.stack.splice(feStackIndex2, 1);           // remove the old formatting element
const fbIndex = state.stack.indexOf(furthestBlock);
state.stack.splice(fbIndex + 1, 0, feClone);    // clone goes AFTER furthestBlock — becomes new current node

Getting this backwards — inserting before furthestBlock instead of after — doesn't crash. It produces a tree that looks almost right, then quietly re-finds the same furthestBlock on the next pass through the outer loop and clones it again. And again. Up to the spec's own 8-iteration safety cap. This is itself a small lesson in malformed-input handling: the algorithm that recovers from malformed HTML has its own internal guard rail (the outer loop's hard 8-pass limit) against recovering from malformed HTML forever. Even the fix-it code is defensively bounded.

Limits — What You Cannot Do Yet

Can't do yet

  • The Noah's Ark clause proper (Module 10's un-built cousin) — this module's >3 pruning branch is implemented but only lightly exercised; none of the three test cases misnest deep enough to trigger it
  • MathML/SVG-namespaced formatting elements interacting with this algorithm — no namespace tracking, consistent since Module 00
  • Multiple simultaneous misnested formatting elements resolving in a single call (each end tag triggers one independent run)

Can do

  • Correctly distinguish the "cheap" (no furthest block) and "expensive" (clone-and-relocate) recovery paths, end to end through the real engine
  • Correctly compose cloning with foster parenting when the misnested element is table-family — zero special-casing between the two mechanisms
  • Terminate correctly within the spec's 8-iteration cap, verified against a real reproduction of the runaway-cloning bug this module's own build hit and fixed

07

Brain Exercise — malformed input, predict the recovery path

For each snippet: does it take the cheap "no furthest block" exit, or the full clone-and-relocate path? Predict before revealing.

1. <p><b>bold</p>normal — a formatting element left open across a </p>

This calls the adoption agency for </p>, not </b> — p isn't a formatting element, so it never reaches this algorithm at all; it's handled by the ordinary "generate implied end tags" machinery this course's engine doesn't implement (Module 13's own noted limit). A genuinely different kind of malformed-input recovery, worth knowing this algorithm does not cover it.

2. <b><b><b>x</b></b></b> — three nested, then three closes, in order

Not malformed at all — every end tag matches the current node exactly. Never reaches the adoption agency's outer loop past its very first "is current node an exact match" fast-path check.

3. <table><b>bold</table></b>after — end tag arrives AFTER the table already auto-closed

Cheap exit — by the time </b> arrives, nothing structural sits between b and the top of the stack (the table-closing machinery already popped past it), so no furthest block is found. Different from this module's own Case 3, where the table is still open when </b> arrives.

4. <b><div><div><div>x</b> — three structural elements piled up before the mismatched close

Full clone-and-relocate — the innermost div found first (nearest the top of the stack) above b is the furthest block, exactly one level deep from b, regardless of how many more structural elements sit above it.

08

There Are No Dumb Questions

Is this really "how the parser handles malformed HTML," or just one narrow piece of it?

One (very complex) piece of a much larger toolkit — Module 12's containment atlas already named seven recovery tactics total (FOSTER, CLOSE, IGNORE, POP+REPROCESS, REDIRECT, MERGE, and ADOPTION AGENCY), each answering a different shape of "the markup doesn't say what to do here." Foster parenting recovers from content landing where a table can't hold it. Scope (Module 13) recovers from an end tag reaching for something it structurally can't touch. This module recovers from formatting-element tags whose start and end straddle a structural boundary — genuinely the most involved of the seven, which is exactly why it was the one piece the original course scope left out. But it's one entry in a larger, already-mapped system, not the whole story by itself.

Why doesn't the parser just... stop, or throw an error, when it sees markup like this?

Because an HTML parser's actual job, since the HTML5 effort standardized it, is to consume any byte stream and produce a tree — never to validate. There is no such thing in the spec as a fatal HTML parse error; every single error condition names a specific, deterministic recovery action, and this algorithm is simply the recovery action for one specific condition. This is a deliberate, load-bearing design choice, not an oversight: the web has decades of markup that was never valid to begin with, and "refuse to render broken pages" was never a viable option for a document format with this much legacy content depending on graceful, convergent recovery.

Real browsers ship an implementation far more complex than this module's ~200 lines. What's actually missing?

Mainly the Noah's Ark clause in full (Module 10's still-unbuilt bound on the active formatting elements list), namespace-aware handling for MathML/SVG formatting elements, and the "generate implied end tags" step this module's own inner loop leans on but Module 13 already flagged as not implemented. None of these change the shape of the algorithm demonstrated here — they're additional edge-case coverage on top of the same three-branch (trivial-pop / no-furthest-block / cloning) structure this module builds and verifies.

The build for this module hit three real bugs and two self-caught test mistakes. Doesn't that undercut confidence in the result?

The opposite, if the process is visible — which is why DECISIONS.md documents every one of them in full rather than presenting a clean-looking final version. Every claim in this tutorial is backed by output re-verified against a real browser using an unambiguous serializer, after two earlier misreadings of that same real output were caught and corrected. That is what "we verify, we don't assume" is supposed to look like when the subject is actually hard — not a promise that mistakes won't happen, but a discipline for catching them before they ship.
