Track 1 · Module 06 · Build phase

What GetsFostered

Foster parenting isn't element-specific — it's a property of the insertion location. This module proves that by fostering an HTML element, two foreign (SVG/MathML) elements, and a lone character, all in one input, and watching all four land in the same relative spot, in source order.

What this module proves

insertForeignElementAtAppropriatePlace() is not a coincidence of matching output — it's the exact same function Module 05 built for HTML elements, and this module's own 2013-bug history explains why the spec insists on that.

01

The Big Analogy

It isn't only people who get walked out the gate. Security escorts out the luggage, the pets, and the entire foreign delegation too — anything that arrives through the front door and isn't on the corridor's list gets the same treatment, because the rule was never "escort out anyone whose passport looks like this." It's "escort out anything landing at this door, full stop." A foreign delegation (MathML/SVG) doesn't get special-cased into staying, because the guard was never checking passports in the first place — only doors.

02

What Happens, Step by Step

  1. insertForeignElementAtAppropriatePlace() is defined as a one-line call-through to Module 05's insertElementAtAppropriatePlace() — same location algorithm, no special casing.
  2. A structural probe builds two byte-identical parser states, inserts an ordinary <div> into one via the HTML-element function and a <math> into the other via the foreign-element function, and asserts the two resulting trees are structurally identical (modulo the tag name itself).
  3. Three real inputs are then run through Module 05's dispatch5 engine, completely unmodified: a bare <math> in a table, a bare <svg> in a table, and a mixed case — <div>, <math>, a character, and <svg>, all inside one table.
  4. All three are asserted against real, independently-captured browser DOMParser output.

Four completely different token kinds, one relocation path, one preserved order.

04

The Code, Explained

The entire module's new logic:

function insertForeignElementAtAppropriatePlace(state, tagName, attrs = new Map()) {
  return insertElementAtAppropriatePlace(state, tagName, attrs);
}

Why this is a named wrapper rather than either a straight re-export or an independent reimplementation — and why that choice is itself the point — is explained in full in DECISIONS.md, alongside the 2013 spec bug this module's test cases are chosen to demonstrate.

05

Limits — What You Cannot Do Yet

Can't do yet

  • Distinguish a foreign element's namespace for any purpose other than fostering — no namespaceURI, no per-namespace attribute-case adjustment
  • Reproduce nodes created by "reconstruct the active formatting elements" being fostered — that's Module 10

Can do

  • Correctly foster an HTML element, a foreign element, or a character token, using the identical underlying mechanism for all three
  • Preserve strict source order across a mix of all three token kinds landing at the same fostered location

07

Brain Exercise

The 2013 bug happened because someone reasoned "a foreign element's current node is always non-HTML by the time it's inserted." Construct the shortest input where that reasoning fails, and say in one sentence why it fails there.

<table><math> — the shortest possible failing case, and the exact one this module tests. It fails because the CURRENT NODE at the moment <math> is being inserted is still the HTML <table> element — the foreign element hasn't been inserted yet, so nothing foreign is on the stack at all. The reasoning conflated "the node being inserted is foreign" with "the current node is foreign," which are only the same thing for the SECOND foreign element onward inside a foreign subtree, never the first.

08

There Are No Dumb Questions

If the two functions are this similar, why not just delete insertForeignElementAtAppropriatePlace entirely and have callers use insertElementAtAppropriatePlace directly?

Because the name itself is documentation. A future module's code that reads insertForeignElementAtAppropriatePlace(state, 'math') states its intent (this is a foreign element, deliberately) in a way that calling the HTML-element function directly for a <math> tag wouldn't. The wrapper costs one function and one import; the clarity it buys at every call site is worth it, and DECISIONS.md explains why a wrapper (not a re-export, not a duplicate) is the specific form that earns that clarity honestly.

Why does the demo build a "structural probe" by hand instead of just trusting that matching real-browser output for Cases A/B/C is proof enough?

Because matching output is proof the answer is right, not proof of why it's right. A parser that happened to hardcode "if tagName is math or svg, insert before the nearest table" would also pass Cases A, B, and C — and would also be a ticking time bond the moment a new foreign element name showed up. The structural probe instead asks the more general question directly: given the same state, do the two functions do the same thing? That generalizes to every foreign element, not just the two tested.
