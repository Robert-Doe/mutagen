Reconstruct the ActiveFormatting Elements

The algorithm this module actually builds. Checks one question — is the most recent formatting element still open? — and, if not, re-opens exactly enough of them.

A standing guest list, checked at the door every time new content arrives. If the most recent name on the list already has a valid badge (is on the stack), nothing happens — move on. If not, door staff issue a brand-new badge for that name, and every name after it on the list, in order. The new badges aren't the old ones, reactivated. They're new badges, freshly cut, that happen to have the same names printed on them.

When it runs: before certain insertions in in body — this course's engine calls it before character-token insertion and before inserting a formatting-element start tag (see Module 10's DECISIONS.md for exactly where; not universal in this simplified engine).

Step 1: empty list → do nothing.

Step 2: last entry is a marker, or is already on the stack of open elements → do nothing. This is the check that fails right after table cleanup has silently popped a formatting element off the stack without telling the list.

Steps 3+: walk backward to the earliest entry needing recreation, then forward, inserting a fresh element for each and replacing the list's entry with the new object.

Each freshly inserted element goes through the exact same "appropriate place for inserting a node" call every other insertion in this engine uses — which is the entire reason reconstruction can end up fostering.

The confused pair

"Reconstruction" sounds like it should mean rebuilding a damaged tree, or undoing a mistake. It doesn't undo anything — it's a proactive, routine check that runs on essentially every relevant insertion, most of the time finding nothing to do (step 2's early exit). The triple-<b> case is what happens on the rare token where step 2 doesn't exit early — not a special "repair mode," just the same routine check with a different answer.

How this connects

Reconstruction and the adoption agency both read and write the active formatting elements list, but do opposite jobs: reconstruction adds entries back (as new elements) when the stack has fallen behind the list; the adoption agency removes/relocates entries when the stack and list disagree about nesting order, not membership. Reconstruction's fostering behavior is entirely inherited from foster parenting — it contains no fostering logic of its own. Shares nothing with DOM reparenting.
