Formatting Elements &the Triple <b>

This is where foster parenting stops being a local rule and starts interacting with the parser's other error-recovery machine. One <b> tag, one real spec example, three separate <b> element objects in the final tree.

What this module proves

<table><b><tr><td>aaa</td></tr>bbb</table>ccc — the spec's own §13.2.10.3 example — produces three distinct <b> objects, verified by object-identity checks, matching real browser output exactly.

01

The Big Analogy

Formatting elements keep two independent records: a badge on the lanyard rack (the stack of open elements — "currently inside") and a name on the standing guest list (the active formatting elements list — "should be wrapped around whatever comes next"). Table-structural cleanup — the operation that clears the way for a new row — confiscates badges. It has no authority over the guest list; that's a completely different desk's job.

So when a name is still on the guest list but its badge got confiscated, the next time content shows up, the door staff dutifully mint a fresh badge for the same name. Not the same badge, reissued. A new one. And if it happens again, another new one.

02

What Happens, Step by Step

  1. <table> — ordinary insertion, mode switches to in table.
  2. <b> — unhandled in in table, so it falls to the anything-else fallback: fostered before the table, pushed onto BOTH the stack and the active-formatting list.
  3. <tr> — clearStackBackToTableContext pops the <b> off the stack. It stays on the list. Implied <tbody>, then <tr>.
  4. <td> — inserted, then a marker is pushed onto the formatting list.
  5. "aaa" — reconstruction runs but stops immediately: the list's last entry is the marker.
  6. </td> — the list is cleared back to (and including) the marker, exposing the <b> entry again.
  7. "bbb" — buffered (Module 08), then flushed with fostering enabled. Reconstruction now finds <b> on the list but NOT on the stack → creates a brand-new <b>, itself fostered (current node is tr, a fostering target).
  8. </table> — pops through the second <b> and the table; mode reverts to in body.
  9. "ccc" — reconstruction fires again → a THIRD <b>. Flag is off now (mode is plain in body), current node is body, so it's appended normally, right after the table.

Same reconstruction call, invoked three completely different times, produces three completely different outcomes — entirely dictated by whatever the current node happens to be at each moment it fires.

04

The Code, Explained

The one line that makes reconstruction automatically inherit fostering, with no special-casing:

for (; i < list.length; i += 1) {
  const entry = list[i];
  const clone = insertElementFn(state, entry.tagName, entry.attrs);  // same fn every module uses
  list[i] = clone;
}

And the divergence itself — table cleanup touches only the stack, never the list:

function clearStackBackToTableContext(state) {
  while (state.stack.length > 0 && !TABLE_CONTEXT_STOP_TAGS.has(currentNode(state).tagName)) {
    state.stack.pop();  // the list of active formatting elements is never touched here
  }
}

Full rationale, including why a narrow, targeted </table>-closing rule had to be added specifically to reach the third <b>, is in DECISIONS.md.

05

Limits — What You Cannot Do Yet

Can't do yet

  • Handle any formatting element besides <b> — the set is deliberately narrow
  • Bound reconstruction cost with the Noah's Ark clause (3+ duplicate entries)
  • Run the full adoption agency algorithm — only reconstruction and stack-clearing, its close relatives, are built here
  • Close a table in the general case — only the narrow rule this module's own test needed

Can do

  • Reproduce the spec's own canonical triple-<b> example exactly, including three distinct object identities
  • Correctly skip reconstruction while inside a cell (via markers) and resume it once the cell closes

07

Brain Exercise — the near-miss

<b><table>foo</table></b> does NOT duplicate — work out why before reading on.

Because there the <b> was opened before the table and is still on the stack when foo arrives — reconstruction's step 2 bails immediately (the list's last entry IS on the stack). The text is fostered directly into the existing <b>, giving <b>foo<table></table></b>. Duplication needs the stack/list divergence, and only "clear the stack back to a table context" manufactures it — a <b> that was never on the stack when clearing happened has nothing to diverge from.

08

There Are No Dumb Questions

Why does clearing the stack leave the list untouched — wouldn't it be simpler for one operation to just clean up both?

Because they answer different questions, for different consumers. The stack answers "what's currently open, structurally" — table cleanup cares about that and nothing else, since its whole job is getting the tree back to a sane table-structural state. The list answers "what formatting should wrap future content" — a question table cleanup was never asked and has no business answering. The bug (or rather, the deliberate design) is that nobody ELSE is responsible for reconciling the two after table cleanup runs — reconstruction just quietly re-derives what's missing, later, whenever it's next needed.

The three <b> elements are three different JavaScript objects. Does the demo prove that, or just that the final tree looks like three <b> tags?

It proves object identity directly — assert.notEqual(bElements[0], bElements[1]) and the same for the second/third pair — not just that three <b>-tagged nodes exist in the serialized output. This matters for the same reason Module 09 insisted on === checks: a tree-shape match alone can't distinguish "three genuinely separate elements" from some hypothetical (and wrong) implementation that reused one object with cloned-looking siblings.

Why did this module need to add a table-closing rule when three prior modules (05, 07, 08) all deliberately stopped short of building one?

Because the third <b> — the whole point of the spec's canonical example — only exists on the far side of </table> closing successfully. Modules 05, 07, and 08 each had complete, provable claims that didn't require going past that boundary; this module's claim (three DIFFERENT outcomes for reconstruction, one per position relative to the table) structurally requires reaching all three positions, including the one after the table is gone. DECISIONS.md is explicit that the rule added is narrow and targeted, not a general "close tables properly" — that's still future work.
