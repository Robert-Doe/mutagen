FosterParenting

A parser flag, live for exactly one token, that changes where a node gets inserted. Nothing more.

A security guard who isn't stationed anywhere. He's summoned for exactly one arrival, escorts them to a specific spot on the pavement, and leaves. He never decides who gets summoned — that's a separate gate check (Module 02's two conditions). He never decides what happens to anyone already inside — that's a different mechanism entirely (see adoption agency).

What it is: state.fosterParentingEnabled, a boolean with a one-token lifetime (Module 03).

What it does: when true AND the current node is table-family (Module 02, Module 04), it changes step 2 of "appropriate place for inserting a node" (Prerequisite P5) to compute a different destination — one hop before the nearest open table (Module 05).

What it does NOT do: decide which elements get duplicated when reconstructed (that's reconstruction's job, this module); move already-adopted, already-misnested formatting elements around after the fact (that's the adoption agency's job); or correspond to any DOM API a script author can call directly (see reparenting).

How this connects

Foster parenting is the mechanism the other three terms on this page interact with, not a peer of theirs. Reconstruction can trigger foster parenting (Module 10: reconstructing a <b> while current node is table-family fosters it). The adoption agency's final relocation step routes through the exact same "appropriate place" algorithm foster parenting lives in — so it can foster too, but it's a much larger algorithm doing a different job. DOM reparenting shares only a name's overlap with none of the mechanism.
