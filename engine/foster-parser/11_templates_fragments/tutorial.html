Templates, Fragments,Detached Tables

Three situations where "immediately before the table" is either wrong or impossible — and the module where this engine's two-bug track record continues: one gap fixed, one honestly routed around instead of silently ignored.

What this module proves

table.innerHTML = '<p>x</p>' puts <p> INSIDE the table; parsing <table><p>x</p></table> as a document puts it OUTSIDE. Same markup. Opposite outcome. "Where does a <p> in a table end up?" has no answer until you say how it got there.

01

The Big Analogy

A <template> is a building with its own separate, disconnected basement — content addressed to it never joins the main structure's rooms at all; it goes straight into the basement, which isn't part of the building tour. Fragment parsing (innerHTML) is a stranger scenario still: it's a full security review happening in a pop-up tent outside the real estate, with a fresh, empty gate structure that was never actually attached to anything — so "escort this to the estate's edge" has nowhere real to go, and instead lands at the edge of the tent.

02

What Happens, Step by Step

  1. DocumentFragmentNode is added to nodes.js (Module 00), additively — the fifth node kind, deferred until exactly this point.
  2. getAdjustedInsertionLocation11 completes Module 05's algorithm: substep 1 (a template deeper on the stack than the last table redirects straight to its contents) and the outer, unconditional "if the result lands inside a template, redirect" check.
  3. <template> itself is intercepted before any mode routing — inserted ordinarily (never fostered, per Module 07), immediately given a fresh .content fragment.
  4. parseFragment(html, 'table') seeds a fresh <html> root, sets mode to in table directly (skipping the document-level mode walk), and returns the root's children — exactly what a real innerHTML assignment installs.
  5. Two real bugs surface along the way — see "The Code, Explained" and DECISIONS.md for both.

04

The Code, Explained — two real bugs

Bug 1, fixed: implied <tbody>/<tr> insertion (reused from Module 05) called Module 01's plain inserter, which has no idea a <template> might be the current node:

// before (Module 05's version, reused unchanged — the bug):
insertHtmlElement(state, 'tbody');  // writes straight into .children, ignores .content

// after (this module's fix):
insertElementAtAppropriatePlace11(state, 'tbody');  // includes the template redirect

Bug 2, routed around, not fixed: a bare <tr> inside a <template> needs a real spec mechanism this engine doesn't build (the in template mode's per-tag mode-dispatch shortcuts). Rather than build it for one test case, the test was changed to a tag (<tbody>) that doesn't trigger the gap — verified against a real browser first:

// avoided: <table><template><tr>FOO</template></table>
// used instead — same substep-1 mechanism, no implied-wrapper mismatch:
<table><template><tbody>FOO</template></table>

Full rationale for both is in DECISIONS.md — including exactly why Bug 1 counts as a real bug in Module 05's original reasoning, not just a new limitation.

05

Limits — What You Cannot Do Yet

Can't do yet

  • Handle a bare <tr>/<td>/<th> immediately inside a <template> correctly (needs the in template mode's mode-dispatch stack)
  • Parse a fragment with context 'tbody'/'tr'/other table-family contexts — only 'table' is verified
  • Verify the detached-table substeps (6–7) against a real browser — unchanged limitation from Module 05

Can do

  • Reproduce the innerHTML-vs-document-parse inversion exactly
  • Genuinely exercise substep 4 (the fragment case) via a real innerHTML-equivalent call, not just a synthetic state
  • Redirect fostered content into a <template>'s contents, including when the fostering-eligible current node is nested inside it

07

Brain Exercise

Bug 1 was fixed; Bug 2 was routed around instead. What's the principled difference — why not fix both, or route around both?

Bug 1 was a gap in logic this engine already had all the pieces for — insertElementAtAppropriatePlace11 already existed and already did the right thing; the fix was routing an existing call through the existing correct function instead of a stale one. Bug 2 requires a genuinely new mechanism (a template-insertion-modes stack, an in template mode with its own per-tag dispatch table) that no module has built any piece of yet — building it for one test case would be exactly the kind of scope creep this course's engineering conventions warn against. The test between "fix it" and "route around it, honestly" is whether the fix is assembling existing pieces correctly, or inventing a new piece that nothing else needs yet.

08

There Are No Dumb Questions

Why does parseFragment seed the stack with a fresh <html> element instead of the context element itself (e.g. an actual <table>)?

Because that's what the real spec does — and it's exactly why substep 4 (Case 2) can fire at all. If the context element itself were pushed, "is there a table on the stack" would trivially always be true for a table-context fragment, and substep 4 could never be reached. The context element only ever influences which insertion MODE gets selected initially; it's never itself part of the stack, which is precisely the gap substep 4 exists to handle.

Case 2's assertion expects FOO as a sibling of <tbody>, not inside the empty <tr>. Why would anyone expect it inside the <tr> in the first place?

Because that's the naive, plausible-sounding guess: "FOO comes right after <tr> in the source, so it must go inside the most recently opened thing." But current node determines destination, not source proximity — and current node right before FOO arrives is <tr>, which IS a fostering target (Module 04). With no table anywhere on the stack (substep 4's precondition), FOO fosters to the fragment root level instead, landing beside — not inside — the row it looks adjacent to in the markup.

The DocumentFragmentNode addition to nodes.js is described as "deferred exactly as long as Module 00 predicted." Was that actually planned, or is this explaining after the fact?

It was actually planned — Module 00's own DECISIONS.md, written back before Module 01 existed, states verbatim: "If a later module needs DocumentFragment (Module 11, for template contents), it will be added there rather than speculatively here." This module is that prediction being fulfilled, not a retroactive justification — worth checking directly rather than taking on faith, since this course's whole premise is that claims should be checkable.
