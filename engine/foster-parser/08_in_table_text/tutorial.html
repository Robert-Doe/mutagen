Track 1 · Module 08 · Build phase

"in table text"& the Whitespace Trap

Characters arrive one at a time (Prerequisite P1). This module is where that granularity finally matters: a whole run of them gets buffered, and one single non-whitespace character anywhere in the run is enough to drag every character in it — spaces included — out of the table together.

What this module proves

In <table><tr><td>a</td></tr>\n  x</table>, the newline and two spaces before x travel with it — fused into one "\n x" text node, fostered before the table, even though the newline alone would have been fine.

01

The Big Analogy

Text doesn't arrive one person at a time — it arrives as a coach party. Security doesn't check them individually at the door; the whole party waits in a holding pen until the coach empties, and then one decision is made about all of them at once. If every passenger is a harmless space character, the whole party is waved through. If one single passenger is a real character, the entire coach is escorted out — spaces included, even the ones that were fine on their own.

02

What Happens, Step by Step

  1. A Character token arrives while state.mode === 'in table'. Instead of processing it, enterInTableText() clears state.pendingCharacters, saves the current mode as state.originalMode, and switches to 'in table text'.
  2. The triggering token is reprocessed under the new mode — handleInTableText() pushes it onto pendingCharacters and returns, emitting nothing.
  3. Every further Character token does the same: buffer, emit nothing.
  4. The first non-character token ends the run. handleInTableText() checks: does any buffered character fail the ASCII-whitespace test?
  5. If yes: enable the flag, replay every buffered character through insertCharacterAtAppropriatePlace (Module 05), disable the flag. If no: replay them the same way, without enabling the flag.
  6. Mode reverts to originalMode, and the token that ended the run is handed back to the ordinary dispatcher — it was never actually processed, only used as a signal that the run was over.

04

The Code, Explained

The whole decision, made once per run:

const pending = state.pendingCharacters;
const hasNonWhitespace = pending.some((ch) => !ASCII_WHITESPACE.test(ch));

if (hasNonWhitespace) {
  state.fosterParentingEnabled = true;
  try {
    for (const ch of pending) insertCharacterAtAppropriatePlace(state, ch);
  } finally {
    state.fosterParentingEnabled = false;
  }
} else {
  for (const ch of pending) insertCharacterAtAppropriatePlace(state, ch);
}

Notice both branches call the exact same loop — the only difference is whether the flag is enabled around it. Full rationale, including an honest analysis of why this module's buffering also (harmlessly) fires for content inside a <td>, where the real spec wouldn't buffer at all, is in DECISIONS.md.

05

Limits — What You Cannot Do Yet

Can't do yet

  • Distinguish "in table text" (real buffering) from "in cell, no buffering at all" by mode alone — this engine's collapsed modes mean both look like 'in table'
  • Model a NULL character token inside a buffered run as its own parse-error case (the spec has one; no test input here needs it)

Can do

  • Correctly buffer and flush a mixed whitespace/non-whitespace run, fostering all of it together
  • Correctly insert an all-whitespace run in place, with no parse error
  • Prove, via a real test case rather than an assumption, that its mode-collapsing simplification doesn't change tree-shape output even inside a <td>

Getting a blank or broken result?

If the whitespace run ends up split into multiple text nodes instead of one fused "\n x", check that insertCharacterAtAppropriatePlace is being called once per buffered character in a simple loop — inserting the whole buffered string as one token instead would skip the fusion check entirely for the first character against whatever was already there.

07

Brain Exercise

Why does the spec buffer characters at all here, instead of testing each one as it arrives and deciding immediately whether to foster it?

Because the decision is a property of the whole run, not of any single character — a space arriving before you know whether a letter follows can't be classified yet. Insert it eagerly inside the table, and you can't retract that decision when the letter shows up two tokens later. Buffering defers the choice until the run is closed by a non-character token, then relocates the whole run atomically — which is also exactly what makes the fused text node in this module's test a single append rather than a sequence of corrections.

08

There Are No Dumb Questions

DECISIONS.md admits this module's buffering fires even for content inside a <td>, where the real spec wouldn't buffer at all. Isn't that just wrong?

It's a real divergence from the spec's mechanism, but not from its output — and DECISIONS.md doesn't paper over the difference, it proves the output claim directly with this module's first test case (content inside a real <td>, correctly landing inside it despite being routed through buffering). The reasoning: buffering only delays when insertCharacterAtAppropriatePlace gets called, never changes the current node it's called against, and Module 02's gate already filters on current-node identity regardless of the flag's spurious state. If a future module's test case ever contradicted that argument, this module's claim would need revisiting — but none does.

Why replay the buffered characters one at a time through insertCharacterAtAppropriatePlace instead of just building the whole string and inserting it as one TextNode directly?

Because "insert one big string" would have to separately reimplement the fusion check against whatever's already at the destination — and would still need a loop internally if the destination changes mid-run (it doesn't, in this module's tests, but nothing about the algorithm guarantees that in general). Calling the existing per-character function in a loop means Module 00's tryFuseCharacter, Module 05's location algorithm, and this module's buffering all compose for free, with zero new fusion logic — which is exactly the claim this module's DECISIONS.md makes about why no special-casing was needed.

What's Next

Module 09 looks even more closely at the fusion this module leaned on without building anything new for it — specifically the case where fostered text lands next to a text node that wasn't part of the same buffered run at all, on the opposite side of an entire <table> element.
