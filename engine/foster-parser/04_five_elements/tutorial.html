Track 1 · Module 04 · Build phase

Why ExactlyFive Elements

Not four, not six. This module tests eleven table-related-or-not elements one at a time and shows the five-element list isn't a list to memorize — it falls out of one question, asked of each element: "if a stray node landed here, would it have anywhere sensible to go?"

What this module proves

table, tbody, thead, tfoot, tr — and only those five, out of eleven tested — gate isFosterParentingTarget() true, exactly matching Module 02's FOSTER_PARENT_TARGETS, derived here element-by-element instead of asserted as a given.

01

The Big Analogy

Walk the whole building from Module 00's factory analogy, room by room, and ask the same question at every door: "if a piece of stray material got left here, is there a shelf?" Some rooms obviously have shelves — a cell (<td>) is built to hold things, so is a caption. Some rooms are pure hallway — no shelf anywhere, nothing to do with stray material but relocate it. The five that foster are exactly the pure hallways. Everything else either has a shelf, or (for two elements) never has the door open to begin with while security is on duty.

02

What Happens, Step by Step

  1. TABLE_FAMILY_ATLAS lists eleven elements: the five fosterers, three flow-content cells/captions that don't, two structurally-excluded near-misses (colgroup, col), and one unrelated control (div).
  2. For each, checkTarget(tag) builds a minimal state with that element as the sole stack entry and the flag enabled, then asks Module 02's isFosterParentingTarget().
  3. The demo prints every row's predicted vs. actual result side by side with its reason, and asserts they match for all eleven.
  4. It separately asserts the set of elements that actually returned true equals Module 02's FOSTER_PARENT_TARGETS exactly — five, no more, no fewer.

The Code, Explained

One row from the atlas, showing the shape every entry shares:

{ tag: 'tr', fosters: true,
  reason: 'CSS display:table-row has no box of its own that isn\'t made of cells' },

And the function that turns "current node is X" into a real, checkable answer without driving a full parse:

function checkTarget(tag) {
  const state = {
    fosterParentingEnabled: true, stack: [new ElementNode(tag)]
  };
  return isFosterParentingTarget(state);
}

Why colgroup and col's rows are honestly marked as "not yet mechanically enforced" rather than silently tested the same way as the other nine is explained in full in DECISIONS.md.

07

Brain Exercise

The atlas includes colgroup and col with reasons this engine doesn't yet mechanically enforce. Suppose a future module (a real "in column group" mode) gets built and it turns out a bug lets colgroup become the current node while the flag is live. Would this module's test catch that regression?

No — and that's worth sitting with. This module's checkTarget() constructs a synthetic state directly; it never asks "can a real parse actually put colgroup here?", only "if it were here, would the predicate say yes?" A regression in a future mode's rules that made colgroup reachable as current node would need a different test — one that drives the real dispatch loop — to catch. This is a real limitation of this module's approach, not a hidden guarantee; DECISIONS.md flags it explicitly rather than letting the green checkmarks imply more than they prove.

08

There Are No Dumb Questions

Why not just trust Module 02's FOSTER_PARENT_TARGETS and skip this module entirely — isn't testing "does the Set contain what the Set contains" circular?

It would be circular if this module tested the Set against itself. It doesn't — it tests the Set's consequences (what isFosterParentingTarget() actually returns for eleven real element names) against independently-stated reasons (CSS box generation, content models, spec mechanisms). The assertion that ties them together — "the elements that return true must equal the Set" — is the one place the two connect, and it's exactly the check that would fail if someone edited the Set to a wrong value without updating the reasoning, or vice versa.

Why does td get "content model is flow content" as its reason, but colgroup gets a completely different kind of reason ("popped and reprocessed")? Aren't they both just "not one of the five"?

They're both "not one of the five," but for categorically different reasons, and that distinction is the whole point of this module's atlas. td fails the test because if it were current node with the flag live, it would have somewhere sensible to put a stray node (it's flow content) — the gate correctly says no because condition 2 fails on its merits. colgroup fails differently: the spec's own rules never let it become current node while the flag could be live in the first place — a structural impossibility, not a content-model judgment. Track 1 Module 12 ("the containment atlas") is where this distinction gets its full name: seven different recovery tactics, of which FOSTER is only one.
