Text-NodeFusion

Every module through 08 checked whether the shape of the fused output matches a real browser. This module checks something stronger and unobservable from output alone: is it literally the same object, mutated — or a new one that merely looks identical?

What this module proves

The TextNode object that "abc" produces, captured by direct reference before <table> even exists, is the exact same object — ===, not just equal-looking — after "def" is fostered into it from the other side of the table.

01

The Big Analogy

The pavement outside the gate isn't empty. If someone is already standing there, the new arrival doesn't get their own spot — they get absorbed into the group that's already waiting. Not seated next to — absorbed, as if they'd been there all along. If you checked the guest list five minutes later, you wouldn't find two entries that happen to look like one group. You'd find one entry, updated.

02

What Happens, Step by Step

  1. "abc" is inserted into <div>, ordinarily, before any table exists. A direct reference to the resulting TextNode is captured.
  2. <table> is inserted after it — ordinary insertion, ends up as div's second child.
  3. "d", "e", "f" are fostered — current node is now table, a fostering target — landing, per Module 05, immediately before the table.
  4. After fostering, div.children[0] is compared with === against the reference captured in step 1 — not just checked for equal .data.
  5. A second test repeats the fostering with three fully independent enable/disable cycles (not one shared loop), proving fusion doesn't depend on a particular calling pattern.
  6. A third test runs the same input through the complete dispatch8 engine, confirming the identity guarantee holds end-to-end, not just in isolated calls.

├─ #text "abcdef"

originalTextNode        ← captured before table existed
  === div.children[0]   ← true, after fostering "def"

Only one interpretation survives: mutation of the original object.

04

The Code, Explained

The check that every prior module's tree-shape comparison couldn't make:

const originalTextNode = div.children[0];  // captured BEFORE <table> exists
// ...insert <table>, then foster "d","e","f"...
assert.equal(div.children[0], originalTextNode);  // ===, not deepEqual
assert.equal(originalTextNode.data, 'abcdef');

Why no new production code was needed to make this true — it was already true since Module 00 — and why that's worth stating as its own decision, is in DECISIONS.md.

Limits — What You Cannot Do Yet

Can't do yet

  • Verify object-identity fusion against a real browser directly — DOMParser's serialized output can't distinguish "mutated node" from "new equal-looking node"

Can do

  • Prove, at the object level, that fostered text merges into an existing node rather than creating a new one
  • Prove this holds whether fusion happens inside one loop or across several fully independent calls
  • Prove it holds through the complete parsing engine, not just in isolated calls

07

Brain Exercise

DECISIONS.md says this module ran no fresh live-browser verification, because object identity "isn't observable through DOMParser's output." Is there any way — even a hard one — to actually observe a real browser's node-identity behavior here, rather than just trusting the spec's wording?

Yes, in principle: a MutationObserver watching a live, incrementally-parsed document (e.g. via document.write) would report a characterData mutation on the existing text node if the browser mutates in place, versus a childList mutation adding a new node if it doesn't. DOMParser specifically can't be used for this because it builds the whole document in one shot with no observable intermediate steps — there's no "before" moment to compare against, which is exactly the same problem this module's own test solves by capturing originalTextNode before the table exists in our engine. Setting that up against a real browser was judged not worth the complexity for what the spec already states unambiguously in prose.

08

There Are No Dumb Questions

Does it actually matter, practically, whether fostered text merges into an existing node versus creating a new adjacent one that looks the same?

Enormously, for anything that holds a reference to a DOM node across a mutation — which is exactly Track 2's subject. A sanitizer, a diffing algorithm, or a piece of instrumentation that captured a reference to a text node and expects to still be looking at "the same node" later can be silently invalidated if the parser actually replaces nodes instead of mutating them (or vice versa, if code assumes replacement and gets mutation). This module's proof isn't paranoia about an edge case — it's establishing precisely the guarantee (or its absence) that later security-relevant code has to reason about correctly.

Why does Part 2 bother testing three separate enable/disable cycles when Module 08 already fostered a multi-character run inside one loop?

Because "inside one loop" and "as three independent events" are different claims about robustness. Module 08's run was buffered together and flushed in one pass specifically because the characters arrived consecutively with nothing in between. Part 2 asks a different question: if three fostering decisions happen at completely separate times, with the enable/disable bracket opened and closed fresh each time (as would happen for genuinely isolated characters, not a buffered run), does fusion still work? The answer being yes confirms fusion is a property of the tree at the moment of insertion, not an artifact of a particular call pattern this engine's own modules happen to use.

09

What's Next

Module 10 is where foster parenting stops being a local, self-contained rule and starts interacting with the parser's other major error-recovery machine: the active formatting elements list. The spec's own canonical example turns one <b> tag into three separate <b> elements — and building it will require this course's engine to track, for the first time, a second list alongside the stack of open elements, plus the "clear the stack back to a table context" operation that manufactures the divergence between them.
