01

The Big Analogy

Two entirely different people can tell you a nesting is wrong. The building inspector reads the plans and files a violation — nothing moves, the building stands exactly as drawn. That's a content-model violation: a validator complains, the parser doesn't care. The security staff physically relocate you — and there isn't just one way they do it. Some visitors get walked to the gate (FOSTER). Some get told "you're already on the list, we'll just update your file" (MERGE — this module's new addition). Some get turned away at the door entirely (IGNORE). Foster parenting is only one tactic in a much larger security manual.

04

The Code, Explained

The tactic that gives this module its one new mechanism:

function mergeHtmlAttributes(state, token) {
  const root = state.stack[0];
  for (const [name, value] of token.attrs) {
    if (!root.attrs.has(name)) {
      root.attrs.set(name, value);  // first occurrence wins — never overwrite
    }
  }
}

Why Module 03's mode-borrowing counts as a real REDIRECT while Module 07's simplified template handling doesn't — a judgment call this module states rather than hides — is explained in full in DECISIONS.md.

07

Brain Exercise

The atlas credits Module 01's implied-html/implied-head insertions as examples of the POP+REPROCESS pattern, even though nothing gets popped in those cases (they're pure insert-and-reprocess, no pop). Is that an honest classification?

Partially — and DECISIONS.md is explicit that this is a judgment call, not an exact match. The REAL "POP+REPROCESS" tactic (as ``'s handling of an unexpected tag) specifically pops an element off the stack before reprocessing. Module 01's implied-element cases only insert-then-reprocess, no pop involved. What they share is the "reprocess" half of the pattern, not the "pop" half. A stricter atlas might list these as a distinct, unnamed pattern rather than folding them into POP+REPROCESS — this module chose the looser classification and says so, rather than either overclaiming a perfect match or omitting the connection entirely.

08

There Are No Dumb Questions

Why does the second <html> tag's foo="override" lose to the FIRST tag's foo="1"? Wouldn't "last write wins" be the more familiar default from CSS or JavaScript object spreading?

Familiar from other systems, yes — and exactly why this is worth testing explicitly rather than assuming. HTML's merge rule is first-wins specifically because the root <html> element is created once, early, often before a script or later markup has any chance to reconsider its attributes — the spec treats the ones present at creation time as authoritative, and anything arriving later can only fill in gaps, never override. This is the kind of "easy to get backwards" detail this course's real-browser verification methodology exists to catch.

This module says 7 of 14 tactics are implemented — is 14 the "real" number of containment tactics in HTML, or just how many this course happened to list?

The latter, and the atlas doesn't claim otherwise. Fourteen is how many distinct elements/situations this course's own source material (the attached reference course's Module 10) and this engine's own build history named as worth distinguishing — not an exhaustive enumeration of every element the real HTML spec has an opinion about (there are dozens more, each with their own clause). The count is a snapshot of THIS course's coverage, stated as such.
