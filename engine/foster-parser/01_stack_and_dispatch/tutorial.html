Track 1 · Module 01 · Build phase

Stack &Dispatch Loop

This module builds the engine's first automatic parser: a real HTML string goes in, a tokenizer and an insertion-mode dispatch loop drive it forward with no hand-holding, and we watch it correctly arrive at "in table" for the first time.

What this module proves

A minimal tokenizer plus a six-mode dispatch loop (initial → before html → before head → in head → after head → in body) can walk <!DOCTYPE html><html><head></head><body>hi<table> and land on mode "in table", current node table, stack html>body>table — exactly what a real browser's parser state would be at that instant.

01

The Big Analogy

Module 00 built a filing cabinet (nodes) and a stack of labeled index cards (tokens), by hand, one card at a time. This module hires a clerk.

The clerk sits at one desk at a time — the insertion mode — and has a strict rulebook for that desk only. A card arrives (a token). The clerk checks the rulebook: does it say anything about this kind of card? If yes, follow it — maybe file something, maybe walk to a different desk and start following that desk's rulebook instead ("switch mode"), sometimes even re-reading the same card at the new desk because the old desk didn't know what to do with it ("reprocess").

If the rulebook at the current desk has nothing to say about this card, the clerk stops entirely rather than guessing — that's the "NotImplementedYet" boundary this module deliberately hits, right after correctly walking all the way to the table's front desk for the first time.

02

What Happens, Step by Step

  1. tokenizer.js scans the input string once, left to right, emitting the six token shapes from Module 00 — no lookahead beyond finding the next <, >, or matching quote.
  2. createParserState() creates an empty stack, an empty document, and sets mode = 'initial'.
  3. Each token is handed to dispatch(token, state), which looks up MODES[state.mode] and calls it.
  4. A mode handler may: insert an element (push the stack), insert a character (fuse or create a TextNode), pop the stack, switch state.mode, and/or call dispatch() again to reprocess the same token under the new mode.
  5. On the <table> start tag, in body's handler inserts the table element, pushes it, and switches to in table — then returns without reprocessing (unlike the mode-switches before it, this one fully consumes the token).
  6. The next token (</table>'s end tag) is dispatched against MODES['in table'], which doesn't exist yet — dispatch() throws NotImplementedYet, and the demo catches it as the expected, deliberate stopping point.

04

The Code, Explained

The transition this whole module exists to demonstrate — note it does not call dispatch() again, unlike every mode-switch before it:

'in body'(token, state) {
    if (token.type === 'Character') {
      insertCharacter(state, token.data);
      return;
    }
    if (token.type === 'StartTag' && token.tagName === 'table') {
      // This is the one transition Module 01 exists to prove: reaching "in table"
      // for the first time. Everything "in table" actually does starts Module 02.
      insertHtmlElement(state, token.tagName, token.attrs);
      state.mode = 'in table';
      return;
    }
    throw new NotImplementedYet('in body', token);
  },

And the bug this module's own test caught before this documentation could be written — the initial mode originally reprocessed every token, DOCTYPE included, cascading three implied elements before crashing:

initial(token, state) {
    if (token.type === 'DOCTYPE') {
      // Real rules append a DocumentType node here... A DOCTYPE token is fully
      // consumed by switching modes — it must NOT be reprocessed.
      state.mode = 'before html';
      return;
    }
    state.mode = 'before html';
    dispatch(token, state);
  },

Full rationale, including why the tokenizer is regex-based rather than a full state machine, is in this module's DECISIONS.md — including a section on the bug above.

05

Limits — What You Cannot Do Yet

Can't do yet

  • Do anything once in table mode is entered — no rules exist for it
  • Handle entities (&amp;), RAWTEXT/RCDATA (<script>, <title>), or malformed markup recovery
  • Compute an adjusted insertion location — every insert is "after current node's last child," always
  • Track active formatting elements — that's Module 10

Can do

  • Tokenize a real HTML string end to end for the well-formed subset this course uses
  • Walk six real insertion modes automatically, including implied-element insertion and token reprocessing
  • Correctly detect and report, with a specific typed error, exactly where its own capability ends

07

Brain Exercise

The dispatch loop stops with a thrown error the moment it can't handle a token — it doesn't quietly skip the token and keep going. A "more forgiving" parser might catch the error internally and just ignore anything it doesn't understand. Why would that be a worse design for this specific course, even though real production parsers do have to tolerate malformed input somehow?

Because this course's entire teaching method depends on every module's "what happens" being an exact, verified, assert-checked claim (see the project rule this course follows: "never fabricate a behavior claim you haven't verified"). If unhandled tokens were silently swallowed, a bug in a later module — say, a foster-parenting rule that's subtly wrong — could produce a tree that's close enough to correct that nobody notices, exactly the failure mode Module 00's FAQ warned about ("roughly right tree shapes are how foster-parenting bugs hide"). A loud, typed, specific error is a debugging tool built into the engine's architecture, not just error handling — real production parsers earn their tolerance for malformed input through the same kind of explicit, tested rule tables this course is building one module at a time; they don't get it by silently ignoring what they don't understand either.

08

There Are No Dumb Questions

Why does before html's "anything else" branch insert an implied <html> element instead of just erroring out, if the input didn't actually have an <html> tag?

Because that's spec-accurate, and it's precisely the kind of "the parser builds a tree even from very odd input" behavior this whole course is about. Try opening a browser DevTools console on a page whose source is just hello with no tags at all — you'll still find <html><head></head><body>hello</body></html> in the Elements panel. The parser never refuses to produce a tree; it fills in structure the source omitted. Module 01's before html/before head handlers reproduce exactly this.

Why does the dispatch loop use a plain object (MODES) keyed by mode name instead of, say, a switch statement or a class per mode?

A few reasons converge: it makes MODES[state.mode] a direct, O(1) lookup that mirrors how the spec itself is organized (one numbered section per insertion mode); it makes "this mode isn't implemented" a natural undefined check rather than a switch's awkward default case; and it means each later module can add or replace exactly one property on this object without touching the dispatch mechanism itself — Module 02 will literally add a real 'in table' entry to this same object.

The tokenizer emits one Character token per character, matching Module 00's contract — but wasn't that going to be inefficient for long text runs?

Yes, and this course's engine doesn't care, because it's optimized for spec-fidelity and explainability, not production performance (see ROADMAP.md's explicit scope notes). A real browser's tokenizer is far more efficient internally, but its observable contract with tree construction is still fundamentally "characters arrive individually" — which is exactly why Module 08's "in table text" buffering behavior has to exist at all. Modeling the inefficient-but-accurate version is what makes that later module's lesson land.

Why does dispatch() re-look-up state.mode on every single call, rather than a mode handler directly calling the next mode's function?

Because "reprocess the token" (Prerequisite P4) means literally: re-run the tree-construction dispatcher from scratch against the *current* value of state.mode, which may have just changed. If a handler called another handler function directly instead of going through dispatch(), it would be bypassing the exact mechanism that makes "switch mode, then reprocess" a general, composable operation rather than a special case hand-wired between specific mode pairs.
